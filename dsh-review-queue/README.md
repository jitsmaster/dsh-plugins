# dsh-review-queue

A review queue for DeepSeek Harness (called **Coding Boss Review Queue** on screen and in the phone app; by voice it still answers to "task list"). It collects what is waiting on you from **every session** in one oldest-first list:

- **Done**: a session finished a turn. The card has a task title (written by the model from your request and the reply; the session name sits underneath), a short summary and the full reply one click away. *Send reply* (the default button; Enter in the box sends, Shift+Enter is a new line) continues that session; *Reviewed* just clears the item.
- **Question**: an `ask_user_question` is open. Answer it from the card (pick an option or type your own). Questions with a timeout expire into *Resolved* with the recommended option taken. An expired question stays answerable from *Resolved* (*Answer now (late)*): picking the option the assistant already took is only recorded as confirmed; a different answer is steered into the session if it is still live. A question never leaves the list on its own: only a real timeout (it expires into *Resolved*), your own cancel, an answer, an automatic answer (below), or the session ending closes it. **Auto-answer:** 10 seconds before a *timed* question would time out (the ask's own timeout, else `questionWindowSeconds`, which must match the `ask_user_question` timeout row) and while you have not answered it, the plugin picks the option marked *(Recommended)* for every sub-question, answers the question like a card click (*Resolved*: "Answered automatically with the recommended option"; the assistant receives it as your answer), and adds a done card "Question auto-answered" saying that the Coding Boss Review Queue, not you, chose the option; reply in the session to change course. A question with no timeout (`timeout: -1`, the legacy blocking tool, a plan review) or where any sub-question has no recommended option is never auto-answered; it stays open for you. The plugin cannot see the card's "Take time" or an editing hold, so it may answer while you are still working on the card. Turn it off or change the lead and window with `questionAutoAnswer`, `questionAutoAnswerLeadSeconds` and `questionWindowSeconds` (Config). If the live request merely ends some other way (the browser disconnects, the turn is aborted), the question stays open as *detached* ("The live request ended; your answer is sent to the session") and answering it goes through the session; if DSH no longer holds it, the answer is refused and the question expires into *Resolved*. Every question that ends without an answer writes one line to `review-queue.log` (item id, error name and code, message, seconds, classification).
- **Permission**: a tool needs approval. *Approve* or *Deny* from the card.
- **PR merged**: a pull request was merged (dsh-hooks-tts sees it while polling the PR). The card belongs to the `PR <n>` session that worked on it and offers *Archive session* (archives that session through the workspace registry and stops anything it is still running; the card then goes to Resolved as "Session archived") or *Keep session* (just clears the item). The card also names the follow-up (`... - after PR <n>`) session(s) that were told to start. An item whose session is archived somewhere else, or ended, leaves the list by itself, and a merged-PR item survives a server restart like a done item. Voice reads it ("Item 2. Pull request 5 merged in PR 5.") but does not archive by voice yet.

**Two filter rules.**
- *Done messages with nothing for you are not listed.* The summary step also judges whether the message holds anything to follow up, decide or do by hand. A plain "renamed the helper, 120 tests pass, committed" is moved straight to *Resolved* ("Hidden: nothing for you to do", the tooltip shows its summary, *Reopen* brings it back, a log line records it). A status or progress update ("still waiting for the subagent") is hidden the same way. A question, a choice, a failure or blocker that needs you, a manual step or an approval request is never hidden, and neither is a handoff, a pull request (including a PR-WAIT heartbeat) or a ticket / work item (AB#id) mentioned at the end of the message: the model may only say no, a guard that reads only the last two paragraphs (code removed) for such signals overrides it, and an unsure answer, a model failure or timeout all mean the item is shown. The card appears first and vanishes within a few seconds when the verdict is no.
- *A question you answered in its own session leaves the list immediately.* The plugin watches that session: your reply to the question (or any plain message you send there), or the question's tool call returning, resolves the item as "Answered in the session" on the next snapshot, and an expired question answered there no longer offers a late answer. Answering from the card works as before; a question pending in another session stays. Details and edge cases: [docs/spec.md](docs/spec.md) ("Task-list filter rules").

**Working through the queue:** the next card is selected automatically after you send, review, answer, approve or deny; keyboard `j`/`k` or ↑/↓ move, `r` reads aloud, `e` marks reviewed, `Shift+A` / `Shift+D` approve or deny (Shift so it cannot happen by accident), Esc closes. In a question's *Other answer…* box, Enter sends the answers like *Send answer*, but only when you typed something there and every other question already has an answer (an option or typed text); otherwise it does nothing. The same holds for the late-answer form of an expired question. A filter bar (type chips and text search) appears once there are more than a few items. Unsent replies and half-picked answers survive a reload. Permission cards show the full command, warn about risky ones (recursive delete, force push, hard reset, git clean, piping a download into a shell, elevation, disk tools, writes outside the workspace) and offer *Approve all N identical* (same session, tool and command; never for a risky one). A done card stays until you mark it *Reviewed*, write a message of your own in its session (a user-source message: any message not injected by DSH itself; goal rounds, schedules and question replies do not count) or the session ends; a newer result from the same session no longer replaces it. Automatic closes (a done card or question closed by a session message, a session that ended, a request that died with a restart, a permission request cancelled, the hub ending an item) write a line with the item id and the reason to `review-queue.log`; two close in bulk and log a count only (the paused-session scan and the one-time import of the old queue.json). *Reopen* in Resolved brings back a misclicked *Reviewed* or a hidden result. Full replies are shown as formatted text, and whether a reply's *Full reply* section, a card's expanded state and an expired question's *Answer now (late)* section are open is remembered per item across closing and reopening the overlay and across reloads, and reading aloud stops when you close the overlay, open a session, or the item leaves the queue.

**Android:** the same list as an installable phone web app (`/review-queue/m/`) over Tailscale, paired once with a code, with push notifications that open the item. Setup steps, spec and decisions: [docs/mobile.md](docs/mobile.md) ("Phone setup"); the hub that serves it: [docs/hub.md](docs/hub.md).

The queue is global, so it is an **overlay only** (the right sidebar is per session and is not used). A round-check button in the session header, just left of the right-sidebar button, opens it; Esc, the Close button or the button again closes it; it never closes by itself, not even when the last waiting item is gone, so it can stay open as your main view. *Open session* jumps to the item's session. **▶ Read aloud** on every card speaks the whole message (the full reply of a done item, not the summary; the question with its options; the permission with its reason) and becomes **■ Stop reading**; it uses the dsh-hooks-tts speech stack, so it follows the TTS mute switch (a muted voice is refused with a message), never overlaps an alert and the Ctrl+Alt+M hotkey stops it. Resolved items are kept for 7 days.

**Hotkey:** `Ctrl+Alt+L` toggles the Coding Boss Review Queue from anywhere in the page (also while typing in a field); `Esc` or the same chord closes it. It is handled in the browser tab, so it needs a page refresh after the plugin updates.

Voice control (read, answer, approve, deny by voice) is a later phase; the plugin already exposes a `reviewQueue` service with speakable text for each item. Besides `snapshot`, `read`, `stop`, `answer`, `approve`, `deny`, `reply`, `markReviewed` it has `count()` (`{total, byType:{question, permission, completed}}`, open items only), `first()` (the oldest open item), `readPosition(n)` (reads the open item at 1-based position n and focuses it; errors `empty`, `no-item`), `again()` (reads the last item read once more; `nothing-read`) and `uiCommand('show'|'hide')`. The text of a read is `"Item N."` as a chunk of its own followed by body chunks that do not depend on the position, so the speech cache hits at any position.

## Tip of the day and the session count

**Tip of the day (desktop only).** While the Coding Boss Review Queue has no open item at all, the right panel (the detail pane, empty then) shows a card with a short tip, while the left list keeps only "Nothing waiting on you." (the narrow single-column layout shows the tip under that message): a title, 2 to 4 sentences (each shown as a paragraph of its own, so it is easy to read) that teach one idea with a concrete example, and a category (`algorithms`, `ai` or `agents`): how an agent loop works, tool calling, context windows, RAG, embeddings, prompt caching, evals, big-O, hashing, graph search, dynamic programming, consensus, Bloom filters and so on. Broad general knowledge, never a summary of your work. It is not shown in the phone app, not while any item is open and not in *Resolved*. The topics are session titles, so they go to the model as a delimited block of untrusted data, and an answer that tells the reader to run, install or open something (or has code, links or headings) is rejected, and so is one that points the reader somewhere (a bare domain such as example.com/x) or tells them what to do (visit, download, install, enter your ..., log in, click, turn off your antivirus). Topics that read like instructions to the model are dropped. The tip is always written by a Haiku model (never another one: with no Haiku available a built-in tip is shown). A model-written tip is labelled *AI-generated* on the card; built-in tips are not. The card is a button: click (or Enter / Space) reads title and body aloud through the same speech stack as *Read aloud*, one sentence at a time (the title, then one speech chunk per sentence, never several sentences in one request; a muted voice is refused with a message); click again, or the Stop of the TTS, stops it.
- *How it is made* ([tip.js](tip.js)): the model writes it as JSON `{title, body, category}` (title up to 80 characters, body up to 600, anything else is rejected). Your recent work topics (the session titles of recent open and resolved items and the live titles from the session query, at most 8, each cut to 60 characters, with URLs, paths, e-mail addresses, keys and ids removed) only steer which broad concept it picks; an answer that carries a URL, path or key-looking text is rejected. The category rotates (algorithms, ai, agents) and the last 12 titles are passed so it never repeats.
- *When*: nothing is generated until the desktop overlay is open (and the page is visible: its poll then adds `tip=1`; with the overlay closed, on the phone and for any other caller no tip is attached and no model call is made) and the list is empty and the current tip is missing or older than 5 minutes; then one model call runs (at most one in flight, 30 s limit) and the old tip keeps showing until the new one is ready. With no model, a failing model call or an invalid answer, a built-in tip is used at once ([tip-builtin.js](tip-builtin.js): 39 curated tips, the whole list is shown before any comes back). The provider's error text goes to `review-queue.log` only.
- *Hub mode*: the tip belongs to this app (its model and speaker). The app adds its own tip to the snapshot it serves to its desktop panel when the merged list is empty; the hub and the phone never see it.
- *Go deeper and Use in my code* ([tip-expand.js](tip-expand.js)): two buttons under the tip card (desktop only; the phone has no tip card).
  - *Go deeper* asks a Haiku model for a longer text of the same tip: 2 to 4 paragraphs (at most 1200 characters in all) with one worked example and one pitfall. It is shown under the tip and kept with it, so asking again costs no model call (overlapping requests share one call). With no Haiku the card says "No model is available to write that right now."; a failed call says "The model could not do that. Try again." and is not retried for 20 seconds (the same answer comes back without a model call)
  - *Use in my code* opens a workspace pick (it starts on the last workspace used for a tip todo, else the first listed; the app has no per-workspace history) and a *Draft todo* button. The model writes a todo for a coding agent: find one place in that workspace where the idea of the tip would improve the code, explain it, implement it with a test. It sees the tip, the workspace name and your cleaned recent topics only as delimited untrusted data. The text lands in the existing *+ New todo* form (opened, workspace set, Use SPARC off); **nothing is sent until you press Add todo**. Text already typed in the form is kept and the draft goes after it. With no Haiku, or an answer that is not usable, a fixed template text is used instead.
  - *Hold*: while a longer text is attached or a draft was made, the tip stays for 15 minutes instead of rotating after 5, so it does not change under you (never more than 45 minutes in all, however often you ask).
  - Reading the tip aloud (click the card) now also reads its longer text after the body, one sentence per chunk.
  - Both routes are local to this app (`LOCAL_ROUTES`; the hub answers 403 `local-only`). A longer text with a URL, path, e-mail address, key, code or an instruction to run, install or open something is thrown away; a todo draft with any of those, a shell command, "run this", install/open/visit text a destructive request (delete tests, disable security checks) or one that goes after secrets or sends something somewhere (.env, credentials, "post/send ... to") is replaced by the template, and after a failed model call the same tip and workspace get the template without a new call for 20 seconds. Tip text goes to the model without angle brackets, and a workspace name that talks to the model (ignore, instructions, system prompt, ...) is dropped, like such a topic. The provider's error text is never shown or kept beyond a short log line.
  - *Needs after updating*: restart DSH (and the hub when used), then reload the panel.

**Session count.** The header of the desktop list and the top bar of the phone app show `N working / M open`: N sessions with a turn running, M open (top-level, not archived, not blank) sessions, from the session controller's list ([sessions.js](sessions.js)), cached for 2 s. It is not shown while the numbers are unknown (no controller). The numbers are only kept fresh while somebody looks (an open overlay or the phone within the last minute; the last numbers stay otherwise), so a closed overlay costs no session-list calls. With the hub on the numbers are summed over every running DSH app: each app reports its own with the register and, when they change, through `presence` (an app that is away or gone adds nothing, an older agent adds 0). The count never changes the `snapshotId`; a change wakes the open screens (at most once every 3 s) through the long-poll token's last two parts (`...|<working>/<open>|<tipId>`, only compared when the client sends them).

## Todo: start a session from the list

Add a task here and rely on the list for everything after it. **+ New todo** (Coding Boss Review Queue header, next to *Resolved*) opens a small form: the task (several lines; Ctrl+Enter or *Add todo* submits), a workspace dropdown (*Choose for me* by default, then every workspace by title) and a *Use SPARC* checkbox (off by default). Esc closes the form first, then the list. **What you type is never lost:** the draft (text, workspace, SPARC, and the text before a tune) is saved in the browser on every keystroke, flushed again when the page is hidden or closed, and restored after a reload or a DSH crash, with the form open as you left it. Only a successful *Add todo* clears it; Cancel, Esc and closing the list keep it, and a refused or failed add keeps the text too. **Tune prompt** (next to *Add todo*) rewrites the text with the rules of the prompt-tune skill and puts the result in the box (the text is disabled while the model works, and *Add todo* too); **Undo tune** brings back what you typed; the draft keeps that original, so Undo survives a reload. Nothing is added to the list by tuning. The phone form keeps its draft the same way but has no Tune button. A todo that has started (or was cancelled) sits in *Resolved* and its card has a *Read aloud* button as well, so the todo text can still be heard.

- **Workspace given:** the session is created at once, with no confirmation. The card shows *Starting...* and moves to *Resolved* as "Started in <workspace> (in the background)".
- **Choose for me:** nothing is ever created before you confirm. The plugin suggests a workspace: first the one whose title or folder name appears in the task as a whole word (any case, a unique match wins; "named in the text"), else the workspace where earlier started todos with the same URL project (origin and first path segment, for example `https://dev.example.com/Project`) started, when that is exactly one workspace ("same project as an earlier todo", no model call; the same project in different workspaces is ambiguous), else a pick by the cheapest LLM (the same service as the summaries; it sees the task, the workspaces, a few recent session titles and the last 8 started todos with the workspace each started in; 30 s limit, 600 tokens; an unknown id or any failure means no suggestion). The *Todo* card then reads "Start in <workspace> - <reason>" (or "Pick a workspace (no suggestion: <why>)" when there is none, for example "timed out after 30 s", "no model available", "the model found no clear fit", "the model answered something unusable" or "LLM error: ..."; the same reason and the start of the model's answer are written to `review-queue.log` in the state directory, capped at 256 KB plus one `.old` file) and offers **Start**, **Change workspace** (the dropdown) and **Cancel**. Enter does not start it, and Shift+A, Shift+D and e do nothing on a todo. The card's workspace dropdown shows the suggested workspace already selected (your own pick wins); the model is shown the workspaces as dropdown options and answers `{"select": <option value>, "reason": ...}` (a workspace name instead of the id is accepted too).
- **Started in the background:** the session is created like the handoff follow-ups are (create, rename to the first line of the task, at most 60 characters, or, when the task mentions an Azure DevOps ticket, to `Fix: <title of the ticket> - <number of the ticket>` (see below), then the task as its first prompt, queued). It is not focused and not opened. Its questions, permission requests and "done" results reach this list like any session's, so the list is the only place you need to watch.
- **Azure DevOps ticket in the task:** a work item URL (`.../_workitems/edit/<n>`, or a board URL with `?workitem=<n>`), `AB#<n>` or "ADO ticket <n>" / "work item <n>" / "ticket <n>" (3+ digits) in the task titles the session `Fix: <ticket title> - <n>` (organisation and project come from the URL; a bare number uses `ingeniuxdev/Ingeniux`). The title is read with the REST API and `AZURE_DEVOPS_EXT_PAT` (Basic auth, sent only to dev.azure.com and *.visualstudio.com, never logged); when it cannot be read (no PAT, offline, unknown ticket) the title is made from the first line of the task, with the number kept. dsh-hooks-tts then names the session that continues the PR `PR <pr> - Fix: <ticket title> - <n>` when the PR for this work is created. Tasks without a ticket keep the first-line title. **A prompt you type into any session** that mentions a ticket renames that session the same way (whatever it was called; the lookup runs in the background; a session on hold stays on hold). The first ticket wins: a session that already has a `Fix: ... - <n>` title, and a `PR <n>` session, keep their title. Only your own messages count (not a todo's first prompt, reminders, goal rounds or subagents). Turn it off with `ticketSessionTitles: false` (Config).
- **Open session:** a started card has an *Open session* **button** (also while it is still starting). It never opens by itself.
- **Use SPARC:** the first prompt is the task, then the /sparc flow instructions and the text of ~/.claude/commands/modes/sparc.md (config sparcCommandPath), the same convention as the handoff resume of dsh-hooks-tts. Without the file it asks the session to invoke the modes:sparc skill.
- **Effort (desktop, New session):** a dropdown after *Use SPARC* lists the reasoning efforts of the **default model** (`GET /v1/model-efforts`); *Default (<name>)* is first and is the effort the default model uses now. Picking another one is sent as `effort` and applied to the new session only: the plugin selects the effort for that session, then puts the default model selection back as it was (`agentDefaultModel.saveSelection`; selecting a model in a session also saves it as the default, so there is a short window in which the default is changed and then restored). Default, or an effort equal to the current default effort, makes no call at all. The effort is stored on the todo (`item.effort`, shown on the card as *Effort: High*) and applied when the session starts, also on Retry and after *Start* of a *Choose for me* todo; an effort the model does not have fails the todo with "The effort X is not available for <model>". There is no dropdown for a follow-up, for a model without efforts, or before the list has loaded; the form goes back to Default after an add, and a saved draft keeps the pick. The phone's New todo form has the same field (see docs/mobile.md): the hub answers its `GET /v1/model-efforts` by asking the coordinator app (the most recently desktop-active one), so the list is that app's default model.
- **Failed:** the card is still waiting and shows the error with **Retry** and **Cancel**. Retry starts it again; a session that was already created is reused, not duplicated. A todo that was *starting* when the server restarted comes back as failed.
- **Follow up (desktop):** the switch at the top of the form changes *New session* to *Follow up*. A follow-up sends the text, as a queued prompt, to an **existing** session that you describe in your own words in the *Which session* box (for example "the PR 6563 session"); the workspace dropdown and *Use SPARC* are hidden, and *Tune prompt* still works on the text. Nothing is sent before you confirm: the card suggests a session ("Session: <title> (<workspace>) — <reason>"), the dropdown lists the other sessions, and **Send** posts it ("Sent to <session>" in *Resolved*, with *Open session* and *Read aloud*). A failed send has **Retry** and **Cancel**. While the add is on its way (the server reads the sessions, which takes a few seconds) the form stays open with your text and shows *Adding…*; it clears and closes only once the server has accepted it, and a refusal leaves it open with the text and the reason.
- **PR sessions are not archived while their PR is open.** With dsh-hooks-tts loaded (it provides the context service `prArchiveGuard`), every Archive button here (merged-PR, archive offer, the session history's) and the idle-session *Archive* answer refuse the `PR <n>` session of a pull request that is still open: the card shows *Its pull request is still open, so the session keeps polling it* (error `pr-open`) and nothing is archived, because the session's comment poll would stop. Without that plugin nothing is refused. Switch off with dsh-hooks-tts's `protectPrSessions`.
- **Archive session on every open row.** Each open item that has a session (not a todo) shows an *Archive session* button on the desktop card, one click and no confirm, and on the phone's conversation section (which keeps its confirm sheet). The merged-PR and archive-offer cards have their own button and show no second one. The server decides with a flag on the open items of the snapshot (rchivable): the session is not running a turn (from the session counter's list, so it is kept only while somebody looks) and, with dsh-hooks-tts, it does not poll a PR that is still open (the guard's verdict is cached 30 s). While either is unknown the button is hidden; the flag is part of the long-poll token (a seventh part, the snapshot's archKey; older clients send six and are not held to it), so the button appears or goes as soon as the answer is known. A session with a pending question or permission may be archived. In hub mode each app flags its own items only: items of other apps show no button. Archiving closes the item's done, merged-PR and archive-offer cards of that session; its open question and permission cards are closed at once as "Session archived" (through capture, so no request stays pending).
- **Archive offer (desktop and phone):** a session asks you to archive it by printing a marker line `ARCHIVE-OFFER <reason>` on its own line from a shell or `run_code` call whose own command wrote it (text only read from a file is ignored), or you type `/archive-offer <reason>` in it. An `archive` card appears (chip *Archive*) with **Archive session** (the same `POST /v1/archive` as the merged-PR card: stops what the session still runs, then archives it) and **Keep session**; the phone shows the same card with a confirm sheet. One open card per session (a repeat only updates the reason), nothing is archived before you press the button, subagents never offer, and no push is sent. Off with the setting `archiveOfferCommands: false`.
- **Pasted images (desktop, New session and Follow up):** paste an image (Ctrl+V, for example a screenshot) into the task box and it is attached: a thumbnail with a ✕ appears under the box, up to 5 images of 8 MB (png, jpeg, webp or gif). When the todo starts, the images go into the first prompt of the new session as image parts after the text, so the session sees them. Each image is uploaded on its own to `<stateDir>/todo-images/` (shared by every app and the hub of this PC; removed once the todo starts or is cancelled, and after 7 days at the latest, so a todo that waits for its confirm longer than a week loses them and fails with a message). Images are not kept in the saved draft (a reload keeps the text only). Not on the phone form. A follow-up sends its images as image parts after its text when you confirm the session, and removes the files afterwards.
- **Counting:** a todo counts as waiting while it needs you (waiting for confirmation, or failed), not while it is starting. Voice reads it as "Todo: <task>, start in <workspace>?"; answering a todo by voice is not built yet.

Service for other plugins (ctx.get('reviewQueue')): addTodo(text, { workspaceId?, sparc?, effort?, followUp?, sessions? }) returns { ok, id, state } at once (the session or the suggestion is worked out in the background), confirmTodo(id, { workspaceId?, sessionId? }) (also Retry), cancelTodo(id), workspaces(). `followUp` (the words that describe an existing session, at most 300 characters; not a string is `empty-query`) makes the todo a message for that session instead of a new one (workspaceId and sparc are ignored); `sessions` (candidates `[{ sessionId, title, ... }]`) is what the hub gives, never given by a client: without it the app's own sessions are read. `confirmTodo(id, { sessionId })` sends a follow-up to that session (it must be one of the item's candidates; without it the suggested one) and `workspaceId` is ignored for it. A todo is an item { type: 'todo', text, sparc, state, workspaceId?, workspaceTitle?, suggested?: { workspaceId, title, reason }, suggesting?, error?, sessionId? } with state awaiting-confirm, starting, started (resolved), failed or cancelled (resolved). A **follow-up** item has kind 'followup' and: query (the words), candidates [{ sessionId, title, workspaceTitle?, owner? }] (the suggestion and its alternatives first, then the newest; at most 20 are stored, the model reads up to 60), suggested?: { sessionId, title, reason, workspaceTitle?, owner? } (a keyworded ticket / PR number such as AB#n, PR n, ticket n, work item n in the words, else the cheapest model), suggestNote? (why there is no suggestion), skippedApps? (apps the hub could not ask), targetSessionId and sessionTitle once confirmed (state starting; the prompt's request id is made of the item id and the session, so Retry sends the same request), and, when started, sessionId and resolution { kind: 'followed-up', by: 'card', sessionId }. A send that timed out or was aborted fails with an error that starts `May have been sent: check the session before retrying.` The hub needs the same version as the app for this (docs/hub.md 6.4a).

## On hold: park a session until it can continue

Some sessions have to wait (for a customer, a reviewer, a ticket). A session on hold is an item of type `onhold` in **its own queue**: it is not counted as waiting, never pushed to the phone as a new item and not in *All*. The header shows **On hold (N)** next to *Resolved*; it opens the queue (cards with the reason, the ticket, when it was held and last checked, **Continue** and **Release**). The phone has an **On hold** tab with the same cards.

- **Put a session on hold:** the **Hold…** button on a *Done* card (expanded) or a *Paused* card (desktop and phone; an optional reason), or type `/onhold <reason>` as a message in the session (the message must start with it; the session sees the message too and will answer it), or let the session do it itself by printing a line `ONHOLD <reason>` from a shell or run_code call that wrote that marker itself (text read from a file or a web page and printed back is ignored). `onHoldCommands: false` turns off the typed command and the marker. The card that was held closes as *Put on hold*; the ⏸ title prefix is NOT used (it already means "holds a parked idea", hold-until skill).
- **Held sessions are left alone:** the paused-session scan and the idle check skip them.
- **A ticket is watched:** when the session is on an Azure DevOps ticket (a work item URL or `AB#<n>` in the `/onhold` text, or the title `Fix: <title> - <n>`), every `onHoldCheckMs` (default 10 minutes; first check `onHoldStartMs`, 60 s) the plugin reads the ticket and compares it with the state noted at hold time. A **new comment, a state change, an assignee change or a description change** continues the session: the plugin prompts it itself (queued; the text names the ticket and the kinds of change but never contains a comment, so the session reads the ticket itself), the item closes as *Continued: the ticket changed (...)* and the ordinary *Done* card appears when the session finishes. A session that cannot go on puts itself on hold again with the `ONHOLD` line (the continue prompt says how). Needs `AZURE_DEVOPS_EXT_PAT` in the app's environment: without it the card shows "Could not read the ticket (no-pat)" and nothing continues. A prompt that fails shows "Could not prompt the session (<code>)" and is tried again at the next check.
- **Continue** prompts the session now and closes the hold ("Continued from hold"); **Release** only takes it off hold ("Taken off hold"). A held session cannot be written to from the phone chat (Continue it first).
- **Routes:** `POST /v1/hold {id, reason?}` (a Done or Paused card), `/v1/hold-release {id}`, `/v1/hold-continue {id}`; the phone may use all three. Service: `createOnHold` in [onhold.js](onhold.js), the typed command in [onhold-command.js](onhold-command.js).

## Taskbar badge

On Windows the number of waiting items (the count in the Coding Boss Review Queue header) also shows as a red badge on the app's taskbar button, so you can see from the taskbar whether anything changed. The Desktop window is owned by the Electron main process, so `scripts/taskbar-badge.ps1` finds the window up the host's parent process chain and sets the overlay icon through the shell; `taskbar.js` debounces changes and only sends a changed count. Nine or more shows `9+`; zero removes the badge, as does stopping the plugin. When DSH runs in a browser there is no such window and nothing happens. Turn it off with config `taskbarBadge: false` or env `DSH_RQ_TASKBAR=0`. A DSH server restart loads it; no browser refresh is needed.

## One list for every app (the hub)

By default each DSH app is an agent of one small hub process (`hub/main.js`, started detached by the first app that finds none, Node built-ins only, loopback only) that owns the list, so every app and later the phone show the same items with the same positions; an action on another app's item is carried out by that app. Design, failure modes and the plan: [docs/hub.md](docs/hub.md).

- **Without a hub** the app is standalone: its own items, a one-line notice in the overlay ("Phone sync is off: hub not running (<reason>) ..."), a retry every minute (backing off to 10 minutes). When the hub is lost the other apps' last known items stay visible, read-only, and the app asks for a new hub at once. Nothing captured meanwhile is lost; it is synced when the hub is back.
- **Mode switches** do not carry the focused item or the item being read over.
- **Files** under the state directory: `local/<instance key>.json` (this app's own items, the outbox), `hub.json` (pid, port, protocol of the running hub), `hub.secret`, `hub-process.log` (stdout and stderr of the hub process), `hub/` (the hub's queue, `hub/hub.log`), `review-queue.log` (this app), `hub.config.json` (yours, optional). The old `queue.json` (and `vapid.json` / `push.json`) is imported once by the hub and then left alone. No secret, reply text or title is logged.
- Ending an app says goodbye to the hub; the hub is never stopped by an app.

## Phone: pairing, devices, push

The hub (never an app) owns who may use the list from a phone. Published with `tailscale serve --bg --https=443 http://127.0.0.1:47615` (Tailscale only, no Funnel), the hub stays on loopback; the phone opens `<publicUrl>/review-queue/m/`.

- **Pair a phone.** In the Coding Boss Review Queue press **Phone**, then **Pair a phone**: a one-time code (8 characters, valid 5 minutes, single use, one active code) and the link to open on the phone appear. The phone shows the pairing screen (the code can also come in the link's `#` fragment), asks a name, and keeps a long-lived device token (`rqd_...`, shown once, stored only as a SHA-256 on the PC) in the browser. Five wrong tries kill the code; wrong answers are delayed (0.5 s doubling to 8 s) and tries are rate limited per address and in total.
- **Phones list.** **Phone** also lists every paired phone (name, paired, last seen, Tailscale login, push on/off) with **Revoke** (a lost phone: signed out on its next request, its open long poll ends, its push subscription is deleted) and **Rename**. A phone unused for 180 days is signed out by itself. Phones registered with a pre-hub build (`push.json`) show as "older registration"; they keep receiving pushes and can be revoked too. A warning line appears when a private file's permissions could not be tightened (`icacls`).
- **What a phone may do.** Read the list, answer, late-answer, approve (always with the confirm sheet; risky ones also the press-and-hold; never "all identical" for risky), deny, reply, archive, reviewed, reopen, read a session's chat thread and post a follow-up (`thread`, `post`), and manage its own push settings. Starting todos and opening sessions stay on the desktop. A request that came through `tailscale serve` is never the desktop, whatever it sends.
- **Push.** The hub sends Web Push (VAPID): one notification per type, replaced by tag, 12 h TTL, only the type and the number on the lock screen. A push waits while the desktop Coding Boss Review Queue was looked at in the last 60 s; a finished message is pushed only after the "needs you" verdict; per-device quiet hours hold done / merged items for one digest, permission and question break through.
- **`hub.config.json`** (in the state directory, written by you, no secrets; read at hub start): `publicUrl` (the HTTPS address of the PC on the tailnet; also the allowed Host and Origin), `allowedTailnetLogins` (list of Tailscale logins; when set only these may pair or use a token), `hubPort`, `pushSubject` (the `mailto:`/`https:` contact the push services see; unset, the hub uses the https `publicUrl` origin, which Apple's push service needs, else a `mailto:` on localhost), `staleGraceMs`, `android { packageName, sha256CertFingerprints }` (for `/.well-known/assetlinks.json`).
- **Files** under `hub/`: `devices.json` (hash only), `vapid.json` (the key pair, imported from the old `vapid.json`), `push.json` (subscriptions; endpoints and keys never leave through the API). They and `hub.secret` are cut off from inherited Windows rights with `icacls` (the current user only).

**UI command.** The snapshot carries `ui: { seq, cmd }` (`cmd` is absent until the first command; `seq` starts at 0 per server run and goes up by one per command). A browser tab applies a command only when its `seq` is newer than the last one that tab has seen, never on its first snapshot (a tab opened later uses its own saved open/closed state), and never twice for the same `seq`. It uses the same function as the header button, so the per-browser open/closed state in localStorage still follows. The command wakes waiting long-polls.

Answers: 200 `{ok:true}`; 400 for bad input (`bad-answer`, `bad-decision`, `empty`, `too-long`); 409 when it cannot apply now (`not-open`, `not-completed`, `no-controller`, `not-expired`, `no-session` (the session is no longer live, e.g. after a restart), `not-pending` (the assistant no longer waits on that question), `reply-queued`, or the host's error); 413/415 for body size/type.

## Limits

- Request body 64 KB; reply text 4000 characters; stored text per field 20,000 characters.
- Resolved items are pruned after 7 days (hourly).
- Summaries use the host's LLM service when available and fall back to the last paragraph of the reply. The same call gives the `ACTIONABLE` verdict; without it nothing is ever hidden.
- **Action items stand out.** The summary model puts every sentence that tells you what to do or answer in `<u>**...**</u>`, and a fallback summary keeps such a sentence from the reply's last paragraph. Either way the plugin moves those sentences into a paragraph of their own at the end of the summary (what was done first, then a blank line, then what you must do). Desktop and phone cards show it bold and one step larger than the text around it, not underlined (the full reply, conversation messages, resolved cards, questions and reasons do the same for `<u>**...**</u>`, also when a model spells it `<U>`, leaves out the `**`, escapes it, nests it or leaves it open; the tags themselves are never shown, and everything else in a message stays plain escaped text); spoken read-outs and search treat it as plain words.
