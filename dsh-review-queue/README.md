# dsh-review-queue

A review queue for DeepSeek Harness (called the **Task list** on screen and by voice). It collects what is waiting on you from **every session** in one oldest-first list:

- **Done**: a session finished a turn. The card has a task title (written by the model from your request and the reply; the session name sits underneath), a short summary and the full reply one click away. *Send reply* (the default button; Enter in the box sends, Shift+Enter is a new line) continues that session; *Reviewed* just clears the item.
- **Question**: an `ask_user_question` is open. Answer it from the card (pick an option or type your own). Questions with a timeout expire into *Resolved* with the recommended option taken. An expired question stays answerable from *Resolved* (*Answer now (late)*): picking the option the assistant already took is only recorded as confirmed; a different answer is steered into the session if it is still live. A question never leaves the list on its own: only a real timeout (it expires into *Resolved*), your own cancel, an answer, an automatic answer (below), or the session ending closes it. **Auto-answer:** 10 seconds before a *timed* question would time out (the ask's own timeout, else `questionWindowSeconds`, which must match the `ask_user_question` timeout row) and while you have not answered it, the plugin picks the option marked *(Recommended)* for every sub-question, answers the question like a card click (*Resolved*: "Answered automatically with the recommended option"; the assistant receives it as your answer), and adds a done card "Question auto-answered" saying that the task list, not you, chose the option; reply in the session to change course. A question with no timeout (`timeout: -1`, the legacy blocking tool, a plan review) or where any sub-question has no recommended option is never auto-answered; it stays open for you. The plugin cannot see the card's "Take time" or an editing hold, so it may answer while you are still working on the card. Turn it off or change the lead and window with `questionAutoAnswer`, `questionAutoAnswerLeadSeconds` and `questionWindowSeconds` (Config). If the live request merely ends some other way (the browser disconnects, the turn is aborted), the question stays open as *detached* ("The live request ended; your answer is sent to the session") and answering it goes through the session; if DSH no longer holds it, the answer is refused and the question expires into *Resolved*. Every question that ends without an answer writes one line to `review-queue.log` (item id, error name and code, message, seconds, classification).
- **Permission**: a tool needs approval. *Approve* or *Deny* from the card.
- **PR merged**: a pull request was merged (dsh-hooks-tts sees it while polling the PR). The card belongs to the `PR <n>` session that worked on it and offers *Archive session* (archives that session through the workspace registry and stops anything it is still running; the card then goes to Resolved as "Session archived") or *Keep session* (just clears the item). The card also names the follow-up (`... - after PR <n>`) session(s) that were told to start. An item whose session is archived somewhere else, or ended, leaves the list by itself, and a merged-PR item survives a server restart like a done item. Voice reads it ("Item 2. Pull request 5 merged in PR 5.") but does not archive by voice yet.

**Two filter rules.**
- *Done messages with nothing for you are not listed.* The summary step also judges whether the message holds anything to follow up, decide or do by hand. A plain "renamed the helper, 120 tests pass, committed" is moved straight to *Resolved* ("Hidden: nothing for you to do", the tooltip shows its summary, *Reopen* brings it back, a log line records it). A status or progress update ("still waiting for the subagent") is hidden the same way. A question, a choice, a failure or blocker that needs you, a manual step or an approval request is never hidden, and neither is a handoff, a pull request (including a PR-WAIT heartbeat) or a ticket / work item (AB#id) mentioned at the end of the message: the model may only say no, a guard that reads only the last two paragraphs (code removed) for such signals overrides it, and an unsure answer, a model failure or timeout all mean the item is shown. The card appears first and vanishes within a few seconds when the verdict is no.
- *A question you answered in its own session leaves the list immediately.* The plugin watches that session: your reply to the question (or any plain message you send there), or the question's tool call returning, resolves the item as "Answered in the session" on the next snapshot, and an expired question answered there no longer offers a late answer. Answering from the card works as before; a question pending in another session stays. Details and edge cases: [docs/spec.md](docs/spec.md) ("Task-list filter rules").

**Working through the queue:** the next card is selected automatically after you send, review, answer, approve or deny; keyboard `j`/`k` or ↑/↓ move, `r` reads aloud, `e` marks reviewed, `Shift+A` / `Shift+D` approve or deny (Shift so it cannot happen by accident), Esc closes. In a question's *Other answer…* box, Enter sends the answers like *Send answer*, but only when you typed something there and every other question already has an answer (an option or typed text); otherwise it does nothing. The same holds for the late-answer form of an expired question. A filter bar (type chips and text search) appears once there are more than a few items. Unsent replies and half-picked answers survive a reload. Permission cards show the full command, warn about risky ones (recursive delete, force push, hard reset, git clean, piping a download into a shell, elevation, disk tools, writes outside the workspace) and offer *Approve all N identical* (same session, tool and command; never for a risky one). A done card stays until you mark it *Reviewed*, write a message of your own in its session (a user-source message: any message not injected by DSH itself; goal rounds, schedules and question replies do not count) or the session ends; a newer result from the same session no longer replaces it. Automatic closes (a done card or question closed by a session message, a session that ended, a request that died with a restart, a permission request cancelled, the hub ending an item) write a line with the item id and the reason to `review-queue.log`; two close in bulk and log a count only (the paused-session scan and the one-time import of the old queue.json). *Reopen* in Resolved brings back a misclicked *Reviewed* or a hidden result. Full replies are shown as formatted text, and whether a reply's *Full reply* section (and a card's expanded state) is open is remembered per item across closing and reopening the overlay and across reloads, and reading aloud stops when you close the overlay, open a session, or the item leaves the queue.

**Android:** the same list as an installable phone web app (`/review-queue/m/`) over Tailscale, paired once with a code, with push notifications that open the item. Setup steps, spec and decisions: [docs/mobile.md](docs/mobile.md) ("Phone setup"); the hub that serves it: [docs/hub.md](docs/hub.md).

The queue is global, so it is an **overlay only** (the right sidebar is per session and is not used). A round-check button in the session header, just left of the right-sidebar button, opens it; Esc, the Close button or the button again closes it; it never closes by itself, not even when the last waiting item is gone, so it can stay open as your main view. *Open session* jumps to the item's session. **▶ Read aloud** on every card speaks the whole message (the full reply of a done item, not the summary; the question with its options; the permission with its reason) and becomes **■ Stop reading**; it uses the dsh-hooks-tts speech stack, so it follows the TTS mute switch (a muted voice is refused with a message), never overlaps an alert and the Ctrl+Alt+M hotkey stops it. Resolved items are kept for 7 days.

**Hotkey:** `Ctrl+Alt+L` toggles the task list from anywhere in the page (also while typing in a field); `Esc` or the same chord closes it. It is handled in the browser tab, so it needs a page refresh after the plugin updates.

Voice control (read, answer, approve, deny by voice) is a later phase; the plugin already exposes a `reviewQueue` service with speakable text for each item. Besides `snapshot`, `read`, `stop`, `answer`, `approve`, `deny`, `reply`, `markReviewed` it has `count()` (`{total, byType:{question, permission, completed}}`, open items only), `first()` (the oldest open item), `readPosition(n)` (reads the open item at 1-based position n and focuses it; errors `empty`, `no-item`), `again()` (reads the last item read once more; `nothing-read`) and `uiCommand('show'|'hide')`. The text of a read is `"Item N."` as a chunk of its own followed by body chunks that do not depend on the position, so the speech cache hits at any position.

## Tip of the day and the session count

**Tip of the day (desktop only).** While the Task list has no open item at all, the right panel (the detail pane, empty then) shows a card with a short tip, while the left list keeps only "Nothing waiting on you." (the narrow single-column layout shows the tip under that message): a title, 2 to 4 sentences that teach one idea with a concrete example, and a category (`algorithms`, `ai` or `agents`): how an agent loop works, tool calling, context windows, RAG, embeddings, prompt caching, evals, big-O, hashing, graph search, dynamic programming, consensus, Bloom filters and so on. Broad general knowledge, never a summary of your work. It is not shown in the phone app, not while any item is open and not in *Resolved*. The topics are session titles, so they go to the model as a delimited block of untrusted data, and an answer that tells the reader to run, install or open something (or has code, links or headings) is rejected, and so is one that points the reader somewhere (a bare domain such as example.com/x) or tells them what to do (visit, download, install, enter your ..., log in, click, turn off your antivirus). Topics that read like instructions to the model are dropped. A model-written tip is labelled *AI-generated* on the card; built-in tips are not. The card is a button: click (or Enter / Space) reads title and body aloud through the same speech stack as *Read aloud* (a muted voice is refused with a message); click again, or the Stop of the TTS, stops it.
- *How it is made* ([tip.js](tip.js)): the model writes it as JSON `{title, body, category}` (title up to 80 characters, body up to 600, anything else is rejected). Your recent work topics (the session titles of recent open and resolved items and the live titles from the session query, at most 8, each cut to 60 characters, with URLs, paths, e-mail addresses, keys and ids removed) only steer which broad concept it picks; an answer that carries a URL, path or key-looking text is rejected. The category rotates (algorithms, ai, agents) and the last 12 titles are passed so it never repeats.
- *When*: nothing is generated until the desktop overlay is open (and the page is visible: its poll then adds `tip=1`; with the overlay closed, on the phone and for any other caller no tip is attached and no model call is made) and the list is empty and the current tip is missing or older than 5 minutes; then one model call runs (at most one in flight, 30 s limit) and the old tip keeps showing until the new one is ready. With no model, a failing model call or an invalid answer, a built-in tip is used at once ([tip-builtin.js](tip-builtin.js): 39 curated tips, the whole list is shown before any comes back). The provider's error text goes to `review-queue.log` only.
- *Hub mode*: the tip belongs to this app (its model and speaker). The app adds its own tip to the snapshot it serves to its desktop panel when the merged list is empty; the hub and the phone never see it.

**Session count.** The header of the desktop list and the top bar of the phone app show `N working / M open`: N sessions with a turn running, M open (top-level, not archived, not blank) sessions, from the session controller's list (the one Pause all uses; [sessions.js](sessions.js)), cached for 2 s. It is not shown while the numbers are unknown (no controller). The numbers are only kept fresh while somebody looks (an open overlay or the phone within the last minute; the last numbers stay otherwise), so a closed overlay costs no session-list calls. With the hub on the numbers are summed over every running DSH app: each app reports its own with the register and, when they change, through `presence` (an app that is away or gone adds nothing, an older agent adds 0). The count never changes the `snapshotId`; a change wakes the open screens (at most once every 3 s) through the long-poll token's last two parts (`...|<working>/<open>|<tipId>`, only compared when the client sends them).

## Todo: start a session from the list

Add a task here and rely on the list for everything after it. **+ New todo** (task list header, next to *Resolved*) opens a small form: the task (several lines; Ctrl+Enter or *Add todo* submits), a workspace dropdown (*Choose for me* by default, then every workspace by title) and a *Use SPARC* checkbox (off by default). Esc closes the form first, then the list. **What you type is never lost:** the draft (text, workspace, SPARC, and the text before a tune) is saved in the browser on every keystroke, flushed again when the page is hidden or closed, and restored after a reload or a DSH crash, with the form open as you left it. Only a successful *Add todo* clears it; Cancel, Esc and closing the list keep it, and a refused or failed add keeps the text too. **Tune prompt** (next to *Add todo*) rewrites the text with the rules of the prompt-tune skill and puts the result in the box (the text is disabled while the model works, and *Add todo* too); **Undo tune** brings back what you typed; the draft keeps that original, so Undo survives a reload. Nothing is added to the list by tuning. The phone form keeps its draft the same way but has no Tune button.

- **Workspace given:** the session is created at once, with no confirmation. The card shows *Starting...* and moves to *Resolved* as "Started in <workspace> (in the background)".
- **Choose for me:** nothing is ever created before you confirm. The plugin suggests a workspace: first the one whose title or folder name appears in the task as a whole word (any case, a unique match wins; "named in the text"), else the workspace where earlier started todos with the same URL project (origin and first path segment, for example `https://dev.example.com/Project`) started, when that is exactly one workspace ("same project as an earlier todo", no model call; the same project in different workspaces is ambiguous), else a pick by the cheapest LLM (the same service as the summaries; it sees the task, the workspaces, a few recent session titles and the last 8 started todos with the workspace each started in; 30 s limit, 600 tokens; an unknown id or any failure means no suggestion). The *Todo* card then reads "Start in <workspace> - <reason>" (or "Pick a workspace (no suggestion: <why>)" when there is none, for example "timed out after 30 s", "no model available", "the model found no clear fit", "the model answered something unusable" or "LLM error: ..."; the same reason and the start of the model's answer are written to `review-queue.log` in the state directory, capped at 256 KB plus one `.old` file) and offers **Start**, **Change workspace** (the dropdown) and **Cancel**. Enter does not start it, and Shift+A, Shift+D and e do nothing on a todo. The card's workspace dropdown shows the suggested workspace already selected (your own pick wins); the model is shown the workspaces as dropdown options and answers `{"select": <option value>, "reason": ...}` (a workspace name instead of the id is accepted too).
- **Started in the background:** the session is created like the handoff follow-ups are (create, rename to the first line of the task, at most 60 characters, or, when the task mentions an Azure DevOps ticket, to `Fix: <title of the ticket> - <number of the ticket>` (see below), then the task as its first prompt, queued). It is not focused and not opened. Its questions, permission requests and "done" results reach this list like any session's, so the list is the only place you need to watch.
- **Azure DevOps ticket in the task:** a work item URL (`.../_workitems/edit/<n>`, or a board URL with `?workitem=<n>`), `AB#<n>` or "ADO ticket <n>" / "work item <n>" / "ticket <n>" (3+ digits) in the task titles the session `Fix: <ticket title> - <n>` (organisation and project come from the URL; a bare number uses `ingeniuxdev/Ingeniux`). The title is read with the REST API and `AZURE_DEVOPS_EXT_PAT` (Basic auth, sent only to dev.azure.com and *.visualstudio.com, never logged); when it cannot be read (no PAT, offline, unknown ticket) the title is made from the first line of the task, with the number kept. dsh-hooks-tts then names the session that continues the PR `PR <pr> - Fix: <ticket title> - <n>` when the PR for this work is created. Tasks without a ticket keep the first-line title. **A prompt you type into any session** that mentions a ticket renames that session the same way (whatever it was called; the lookup runs in the background; a session on hold stays on hold). The first ticket wins: a session that already has a `Fix: ... - <n>` title, and a `PR <n>` session, keep their title. Only your own messages count (not a todo's first prompt, reminders, goal rounds or subagents). Turn it off with `ticketSessionTitles: false` (Config).
- **Open session:** a started card has an *Open session* **button** (also while it is still starting). It never opens by itself.
- **Use SPARC:** the first prompt is the task, then the /sparc flow instructions and the text of ~/.claude/commands/modes/sparc.md (config sparcCommandPath), the same convention as the handoff resume of dsh-hooks-tts. Without the file it asks the session to invoke the modes:sparc skill.
- **Failed:** the card is still waiting and shows the error with **Retry** and **Cancel**. Retry starts it again; a session that was already created is reused, not duplicated. A todo that was *starting* when the server restarted comes back as failed.
- **Counting:** a todo counts as waiting while it needs you (waiting for confirmation, or failed), not while it is starting. Voice reads it as "Todo: <task>, start in <workspace>?"; answering a todo by voice is not built yet.

Service for other plugins (ctx.get('reviewQueue')): addTodo(text, { workspaceId?, sparc? }) returns { ok, id, state } at once (the session or the suggestion is worked out in the background), confirmTodo(id, { workspaceId? }) (also Retry), cancelTodo(id), workspaces(). A todo is an item { type: 'todo', text, sparc, state, workspaceId?, workspaceTitle?, suggested?: { workspaceId, title, reason }, suggesting?, error?, sessionId? } with state awaiting-confirm, starting, started (resolved), failed or cancelled (resolved).

## Install

```
dsh plugin --profile <p> add "link:D:/dev/ai/dsh-plugins/dsh-review-queue"
```

(From a DSH source checkout run it as `pnpm dsh plugin --profile <p> add ...`.) Restart the DSH server and refresh the browser page. Remove it with `dsh plugin --profile <p> remove dsh-review-queue`.

Set in the plugin's `config` (see `cordis.patch.yml`); all optional.

| --- | --- | --- |
| `stateDir` | `~/.dsh/review-queue` (`$DSH_HOME/review-queue`) | Where `queue.json` is kept. If unusable the queue works but is not persisted. |
| `ttsClient` | `../dsh-hooks-tts/scripts/tts-client.ps1` | Path of the TTS client script the play button uses. |
| `voice` | `male` | `male` or `female` voice for the play button. |
| `sparcCommandPath` | ~/.claude/commands/modes/sparc.md | The modes:sparc command text a *Use SPARC* todo puts in the new session's first prompt. |

Show the before/after") the *Tune prompt* button gives the model. Lines that ask the model for a rationale (and the "because ..." reason after a suggested default) are left out, and any closing explanation in the answer is removed, so only the final prompt goes in the box. Missing, unreadable or without that section: a short embedded copy of the rules. The model is the same one the summaries use (cheapest available); 60 s limit, 1500 tokens; a trailing `--thorough` in the text selects the thorough profile, concise is the default. |
| `hub` | `true` | `false`, or env `DSH_RQ_HUB=0`, keeps the plugin standalone exactly as before the hub (no agent, no proxy, no launcher, the old `queue.json`). |

| `hubNode` | the host's node, else `node` on PATH | The node executable that runs the hub. |
| `instanceLabel` | `DSH :<web port>` | How this app is named on the other apps' cards and at the hub. |
| `questionAutoAnswer` | `true` | `false` keeps every pending question waiting for you: nothing is answered automatically. Only a timed question (`ask_user_question` in timed mode) is ever answered; the task list answers with the recommended option and says so on a done card ("the task list answered it for you ... you did not choose it"). |
| `questionWindowSeconds` | `120` | How long DSH waits for an answer when the model passes no timeout. **Must match the `ask_user_question` timeout row** (the plugin cannot read it). A question the model gave an explicit timeout uses that timeout; `timeout: -1`, a legacy blocking question and a plan review are never auto-answered. Known limitation: the card's "Take time" and editing holds are not visible to the plugin. A value that is not a positive number means 120. |
| `questionAutoAnswerLeadSeconds` | `10` | How many seconds before its deadline a question with a recommended option for every sub-question is answered with those options (0 turns the auto-answer off). A question without a recommended option is never auto-answered. |
| `doneKeepPerSession` | `20` | How many open done cards one session keeps. A session that never gets a message from you (schedule ticks, goal rounds, background jobs) would pile them up; past the cap the oldest is closed as *trimmed* (a line in `review-queue.log` names it). Not a positive whole number: 20. |
| `sessionCounter` | `{}` | `{ ttlMs, minEmitMs }` of the session count (defaults 2000 and 3000 ms); mostly for tests. |
| `sessionsRefreshMs` | `5000` | How often the session count is looked at, so a change reaches open screens by itself. |
| `dev` | off | `true`, or env `DSH_REVIEW_QUEUE_DEV=1`, enables `POST /v1/dev/ask` which creates fake items (testing only; never enable in a real profile). |


## Taskbar badge

On Windows the number of waiting items (the count in the Task list header) also shows as a red badge on the app's taskbar button, so you can see from the taskbar whether anything changed. The Desktop window is owned by the Electron main process, so `scripts/taskbar-badge.ps1` finds the window up the host's parent process chain and sets the overlay icon through the shell; `taskbar.js` debounces changes and only sends a changed count. Nine or more shows `9+`; zero removes the badge, as does stopping the plugin. When DSH runs in a browser there is no such window and nothing happens. Turn it off with config `taskbarBadge: false` or env `DSH_RQ_TASKBAR=0`. A DSH server restart loads it; no browser refresh is needed.

## One list for every app (the hub)

By default each DSH app is an agent of one small hub process (`hub/main.js`, started detached by the first app that finds none, Node built-ins only, loopback only) that owns the list, so every app and later the phone show the same items with the same positions; an action on another app's item is carried out by that app. Design, failure modes and the plan: [docs/hub.md](docs/hub.md).

- **Without a hub** the app is standalone: its own items, a one-line notice in the overlay ("Phone sync is off: hub not running (<reason>) ..."), a retry every minute (backing off to 10 minutes). When the hub is lost the other apps' last known items stay visible, read-only, and the app asks for a new hub at once. Nothing captured meanwhile is lost; it is synced when the hub is back.
- **Mode switches** do not carry the focused item or the item being read over.
- **Files** under the state directory: `local/<instance key>.json` (this app's own items, the outbox), `hub.json` (pid, port, protocol of the running hub), `hub.secret`, `hub-process.log` (stdout and stderr of the hub process), `hub/` (the hub's queue, `hub/hub.log`), `review-queue.log` (this app), `hub.config.json` (yours, optional). The old `queue.json` (and `vapid.json` / `push.json`) is imported once by the hub and then left alone. No secret, reply text or title is logged.
- Ending an app says goodbye to the hub; the hub is never stopped by an app.

## Phone: pairing, devices, push

The hub (never an app) owns who may use the list from a phone. Published with `tailscale serve --bg --https=443 http://127.0.0.1:47615` (Tailscale only, no Funnel), the hub stays on loopback; the phone opens `<publicUrl>/review-queue/m/`.

- **Pair a phone.** In the task list press **Phone**, then **Pair a phone**: a one-time code (8 characters, valid 5 minutes, single use, one active code) and the link to open on the phone appear. The phone shows the pairing screen (the code can also come in the link's `#` fragment), asks a name, and keeps a long-lived device token (`rqd_...`, shown once, stored only as a SHA-256 on the PC) in the browser. Five wrong tries kill the code; wrong answers are delayed (0.5 s doubling to 8 s) and tries are rate limited per address and in total.
- **Phones list.** **Phone** also lists every paired phone (name, paired, last seen, Tailscale login, push on/off) with **Revoke** (a lost phone: signed out on its next request, its open long poll ends, its push subscription is deleted) and **Rename**. A phone unused for 180 days is signed out by itself. Phones registered with a pre-hub build (`push.json`) show as "older registration"; they keep receiving pushes and can be revoked too. A warning line appears when a private file's permissions could not be tightened (`icacls`).
- **What a phone may do.** Read the list, answer, late-answer, approve (always with the confirm sheet; risky ones also the press-and-hold; never "all identical" for risky), deny, reply, archive, reviewed, reopen, read a session's chat thread and post a follow-up (`thread`, `post`), and manage its own push settings. Starting todos and opening sessions stay on the desktop. A request that came through `tailscale serve` is never the desktop, whatever it sends.
- **Push.** The hub sends Web Push (VAPID): one notification per type, replaced by tag, 12 h TTL, only the type and the number on the lock screen. A push waits while the desktop task list was looked at in the last 60 s; a finished message is pushed only after the "needs you" verdict; per-device quiet hours hold done / merged items for one digest, permission and question break through.
- **`hub.config.json`** (in the state directory, written by you, no secrets; read at hub start): `publicUrl` (the HTTPS address of the PC on the tailnet; also the allowed Host and Origin), `allowedTailnetLogins` (list of Tailscale logins; when set only these may pair or use a token), `hubPort`, `pushSubject` (the `mailto:`/`https:` contact the push services see; unset, the hub uses the https `publicUrl` origin, which Apple's push service needs, else a `mailto:` on localhost), `staleGraceMs`, `android { packageName, sha256CertFingerprints }` (for `/.well-known/assetlinks.json`).
- **Files** under `hub/`: `devices.json` (hash only), `vapid.json` (the key pair, imported from the old `vapid.json`), `push.json` (subscriptions; endpoints and keys never leave through the API). They and `hub.secret` are cut off from inherited Windows rights with `icacls` (the current user only).

## HTTP API

Served on the DSH web server under `/review-queue` (same host/origin fence and cookie auth as the rest of the web UI). JSON only.

| Route | Method | Body | Notes |
| --- | --- | --- | --- |
| `/v1/snapshot` | GET | query `since=<snapshotId>|<focusId>|<readingId>|<uiSeq>`, `wait=<ms>`, `tip=1` (the overlay is open: attach the tip and keep the session numbers fresh), `client=phone` | Open and resolved items, `snapshotId`, `serverNow`, `reading`, `ui`, `sessions: {working, open}` (when known) and, only while no item is open, `tip: {id, title, body, category, at, source: 'model'|'builtin'}`; every item has a `title`; a standalone or degraded app adds `notice: {level, text}` (the overlay shows it as a one-line banner). The overlay adds `&visible=1` while its page is visible. With `since` it long-polls up to 25 s and answers `{unchanged:true, snapshotId}` if nothing changed, including the ui command sequence. Missing trailing parts mean none (ui seq 0), so a token from before `uiSeq` existed only matches while no ui command has been given and otherwise gets a full snapshot. A client that knows them appends `|<working>/<open>|<tipId>`; the server compares only the parts the client sent. |
| `/v1/answer` | POST | `{id, answers:[{id, selected:[...], custom?}]}` | Answers an open question (also a *detached* one, whose live request ended: the answer is steered into the session; `not-pending` / `no-session` when DSH no longer holds it, and the question then expires). |
| `/v1/late-answer` | POST | `{id, answers:[{id, selected:[...], custom?}]}` | Answers an expired question. Same as the recommended option: recorded as `confirmed`, nothing sent. Different: sent into the session (`late-answered`). |
| `/v1/approve`, `/v1/deny` | POST | `{id}` | Permission items. |
| `/v1/reviewed` | POST | `{id}` | Done items only. |
| `/v1/reply` | POST | `{id, text}` | Done items only; queues the text as a prompt to that session. |
| `/v1/thread` | POST | `{id, before?, limit?}` | The chat view of the phone: the last `limit` (default 40, 1 to 100) user / assistant text messages of the item's session, read from its log; `{ok, sessionId, title, messages:[{id, role, text, time?, truncated?}], hasMore, cursor?}`; page back with `before` = `cursor`. **Hub only (`/hub/v1/*`, same origin as the phone app, behind `tailscale serve`):** `POST /hub/v1/pair {code, name}` (public: `{deviceId, token, name}` once; 400 `bad-code`, 429 `rate-limited`, 403 `login-not-allowed`, 409 `too-many-devices`), `GET /hub/v1/session` (device or desktop: who am I), `GET /hub/v1/health` (minimal), `/.well-known/assetlinks.json`; the desktop routes behind the instance routes above are `POST /hub/v1/pairing-codes`, `GET /hub/v1/devices`, `PATCH /hub/v1/devices/<id>`, `POST /hub/v1/devices/<id>/revoke`. A phone sends `Authorization: Bearer rqd_...` on every call and may make 120 requests a minute (the snapshot long poll excluded); every state-changing call needs `Content-Type: application/json` and, when an `Origin` is sent, one of the hub's own origins. `401 auth-required` means pair again.

**UI command.** The snapshot carries `ui: { seq, cmd }` (`cmd` is absent until the first command; `seq` starts at 0 per server run and goes up by one per command). A browser tab applies a command only when its `seq` is newer than the last one that tab has seen, never on its first snapshot (a tab opened later uses its own saved open/closed state), and never twice for the same `seq`. It uses the same function as the header button, so the per-browser open/closed state in localStorage still follows. The command wakes waiting long-polls.

Answers: 200 `{ok:true}`; 400 for bad input (`bad-answer`, `bad-decision`, `empty`, `too-long`); 409 when it cannot apply now (`not-open`, `not-completed`, `no-controller`, `not-expired`, `no-session` (the session is no longer live, e.g. after a restart), `not-pending` (the assistant no longer waits on that question), `reply-queued`, or the host's error); 413/415 for body size/type.

## Limits

- Request body 64 KB; reply text 4000 characters; stored text per field 20,000 characters.
- Resolved items are pruned after 7 days (hourly).
- Summaries use the host's LLM service when available and fall back to the last paragraph of the reply. The same call gives the `ACTIONABLE` verdict; without it nothing is ever hidden.
- **Action items stand out.** The summary model puts every sentence that tells you what to do or answer in `<u>**...**</u>`, and a fallback summary keeps such a sentence from the reply's last paragraph. Either way the plugin moves those sentences into a paragraph of their own at the end of the summary (what was done first, then a blank line, then what you must do). Desktop and phone cards show it bold and one step larger than the text around it, not underlined (the full reply, conversation messages, resolved cards, questions and reasons do the same for `<u>**...**</u>`, also when a model spells it `<U>`, leaves out the `**`, escapes it, nests it or leaves it open; the tags themselves are never shown, and everything else in a message stays plain escaped text); spoken read-outs and search treat it as plain words.
