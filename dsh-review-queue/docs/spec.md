# dsh-review-queue: spec (from the 2026-10-13 grilling)

> **Revision 2026-10-13 (supersedes the sidebar-tab parts below):** the queue is **overlay only**. The right sidebar is per session, so there is no Review tab, no persistence flag and no sidebar-right dependency. The overlay is opened by a button in the session header's utilities slot (`conversation.session.header.utilities`, order 1000, so it sits just left of the right-sidebar button). The overlay itself is one root on `document.body`; state is a single module-level store. Wherever this spec says "sidebar tab", "persistent tab" or "floating anchor button", read "the header button and the overlay".


A **Review** tab in the DSH right sidebar (sibling of dsh-git-view): the user's to-do list of AI work waiting on them. Tab shows a count badge.

## Items (all sessions, all workspaces), sorted by time ascending (oldest first)
- **Completed**: session finished a turn. Card shows session title, workspace/worktree, finish time, an LLM-written 2-3 line summary of what was done (cheapest available DSH model, generated once and cached; falls back to the last paragraph of the reply on failure); full reply behind the expander.
- **Question**: pending ask_user_question. Card shows the full question, all choices with the recommended one marked, time left, and what happens at expiry. Answerable from the card (option buttons). Enter in a question's "Other answer…" box sends the answers like *Send answer* (same `buildAnswers` check and busy guard, once per send) when that box has text and every other question is answered; Shift/Ctrl/Alt/Meta+Enter and IME composition (`isComposing`, keyCode 229) do nothing, and the same holds for the late-answer form. The key legend says so.
- **Todo**: a task the user added to start a new session (see "Todo item" below).
- **Permission**: pending approval ("Approve write file?"), showing tool and arguments, with Approve/Deny. Never expires or auto-resolves; stays until answered or the session ends; shows its age.

## Persistent view (added after the grilling)
The Review tab must stay visible when the user switches sessions; they must never have to re-open it per session.
- Finding: DSH right-sidebar tabs are per session (the sidebar-right `inject(sessionId)` / `controller.openTab(kind, options)` in packages/client/ui-sidebar-right), so a normal tab like Git has to be opened again in every session.
- Design: the plugin keeps a global "Review tab wanted" flag (localStorage, default on once the user opens it the first time). Whenever the selected session changes and has no Review tab, the client opens one through the sidebar-right openTab API (kind = the Review tab kind, without stealing focus from the session's other tabs). Closing the tab by hand clears the flag; re-opening it from the guide sets it again.
- Tab content, expanded cards and scroll position live in one module-level store shared by every session's tab instance (not component state), so switching sessions shows the same list with nothing collapsed or reset.
- Verify at build time which client hook gives the selected-session change and whether openTab can be called from a plugin (ctx.sidebarRightTabs is register-only in dsh-git-view); if not exposed, fall back to a small shim or a DSH change.

## Two surfaces, one list (added after the grilling)
The same queue is shown in two places:
1. **Sidebar tab** (persistent across sessions, see above).
2. **Full-screen overlay**: a container that overlaps the whole app, opened and closed by an **anchor button**, so the task list can use all the screen space.
- Anchor button: a small always-visible floating button (right edge, vertically centred, clear of the bottom-right TTS status pill) showing the waiting-count badge. Click toggles the overlay; Esc or the button closes it; a configurable shortcut is added later.
- The overlay is global, not bound to a session, so switching sessions never closes or resets it. Its open/closed state is remembered across page refreshes.
- Wide layout: master-detail. A compact list on the left (same ascending order), the selected item's full detail on the right (whole question with all options, full reply, summary, reply box). Below a width threshold it falls back to the single-column card list.
- It reuses the same list component, store and API as the sidebar tab; only the container differs. Expanded/selected state is shared, so an item expanded in the sidebar is expanded in the overlay.
- **Open session** closes the overlay (unless pinned open) and jumps to the session.
- Mounting follows the precedent in dsh-hooks-tts/lib/client.js: a host element on document.body rendered with React createRoot, fixed position, high z-index but below DSH modals, themed with the page's light/dark class.
- Voice: "open the queue" / "close the queue" are read-only navigation commands (queue_show / queue_hide), run immediately; "read item two" works with either surface open.

## Tip of the day and the session count (added 2026-10-19)
- **Tip**: only in the desktop overlay's right panel (the detail pane; the left list keeps "Nothing waiting on you.") and, in the narrow single-column layout, under that message, only while there is no open item (not in Resolved, never on the phone). A tip written by a Haiku model only (fallback: curated, also when no Haiku is available) of broad knowledge about algorithms, AI and AI agents: short title, 2 to 4 sentences with one example, category algorithms | ai | agents. Steered by the user's recent work topics (sanitised: no URLs, paths, keys), rotated by category, never repeating the last 12 titles, replaced after 5 minutes, generated only while the overlay is open (tip=1) and the list is empty (one call in flight, 30 s). The body is shown one sentence per paragraph. The card is a button that reads the tip aloud, one sentence per speech chunk (`POST /v1/read-tip`, `reading === 'tip:<id>'`); clicking again stops it. See README "Tip of the day and the session count".
- **Go deeper / Use in my code (added 2026-10-20)**: two buttons under the desktop tip card. *Go deeper*: `POST /v1/tip-deeper {id}`, a Haiku-written 2-4 paragraph text (<= 1200 chars, example + pitfall) cached on the tip and shown under it. *Use in my code*: workspace pick (last used for a tip todo, else first), *Draft todo* (`POST /v1/tip-todo {id, workspaceId}`) puts a Haiku-drafted todo (fixed template when no model) into the New todo form, never sends it, appends after text already typed. The tip is held 15 minutes (not 5) while a longer text is attached or a draft was made, at most 45 minutes in all; a tip that is being generated meanwhile does not replace it. A failed longer text is not retried for 20 s. Local-only routes; model output is validated (no URL, path, key, code or instruction). Not on the phone.
- **Session count**: `N working / M open` in the desktop header and the phone top bar; local counts standalone, summed over the online apps in hub mode; hidden while unknown; never moves the snapshot id.

## Leaving the queue (status = completed)
- Question: answered by the user, or expired and the recommended option was auto-selected (record which option). A question is never auto-dismissed unless it timed out (rule 3 below); the user's own cancel is the only `cancelled` a request produces.
- Auto-answer (added 2026-10-16, revised the same day after review): `capture.js` arms a timer for a captured question ONLY when the request is a timed one (`req.wait.timed === true`; DSH sends `wait: { callId, timed: true }` only for a timed `ask_user_question`) and it has a deadline: the call's own positive `timeout` argument (noted at `tools/pre-execute`) is the window; when the model passed none, the window is config `questionWindowSeconds` (default 120, a finite positive number, else the default), which **must match the `ask_user_question` timeout row** because the tool's configured default is not exposed to plugins. Never armed: a `wait` without `timed` (indefinite card-keyed ask), no `wait` (legacy blocking tool), `timeout: -1` (no deadline, also noted at `tools/pre-execute`), or a request with a question that carries an `intent` (`AskUserQuestionIntent`, a plan review). The timer fires at `window - lead` (lead = config `questionAutoAnswerLeadSeconds`, default 10; 0 or `questionAutoAnswer: false` = off; no timer when the window is not longer than the lead). Known limitation: the plugin cannot see the card's "Take time" or an editing hold, so a question the user is still working on can be answered. When it fires and the question is still pending, every sub-question has a `(Recommended)` option and `cleanAnswers` accepts the batch, the request is answered exactly like a card answer (the model receives the option as the user's answer), the item is resolved `{kind:'answered', by:'auto', answers}` (text "Answered automatically with the recommended option") and a done item is added: title "Question auto-answered", `summary` and `payload.reply` = "The question \"<q, max 120 chars>\" was about to time out, so the task list answered it for you with the recommended option: \"<option>\". The assistant received that as the answer; you did not choose it. Reply in this session to change course." (several questions are listed with their options). It is a normal done card (`summarySource: 'auto'`, `actionable: true`, so it also triggers the phone push); it is never sent to the summarizer and never hidden as no-action. A question where any sub-question has no recommended option is not auto-answered (it stays answerable until DSH expires it). The timer is cleared when the request ends (card or screen answer, abort), when a session event closes the item, and on dispose. Logged as `capture: question <id> auto-answered with the recommended option: <options>`.
- Late answers (added 2026-10-13): an expired question stays answerable from Resolved. If the late answer equals the recommended option the assistant already took, it is only confirmed (resolution `confirmed`, nothing sent). If it differs, it is steered into the live session through `userQuestions.answer(agent, callId, {answers})` and recorded as `late-answered`. After a restart or when the session is gone the answer cannot be delivered (`no-session`).
- Completed: user clicks **Reviewed**, sends a follow-up message from the card's reply box, or writes a message of their own in the session (`agent/pre-step` with a user-source message: no `source` or source `user`, i.e. any message not injected by DSH itself; messages DSH injects, such as source `goal`, `schedule`, `plan-mode`, `user-approval`, `cordis-host-runner`, and question replies (`user-question-reply`) do not close it). A newer done item does not replace older ones (revision 2026-10-16; the old `superseded` resolution and `earlier` count remain only in persisted data, still shown and reopenable). Automatic closes write a log line with the item and the reason: `capture: done item "<title>" closed: the user replied in the session`, `capture: question <id> closed by session: <why>`, `capture: session-ended: closed <n> open item(s) of session <id>`, `capture: permission <id> cancelled: <why>`, `capture: <type> <id> cancelled: its request died with the earlier process` (restart, from index.js and agent/wire.js), `service: item <id> closed as session-ended: ...` / `service: merged-PR item <id> closed: its session was archived elsewhere`, and the hub's `session-ended <type> <id> (<reason>)` (restarted, owner gone, not-in-sync, orphan-expired). Not logged per item: the paused-session scan (`recovered`, a count) and the one-time legacy queue import (`migration`, a count by design); `store.reconcile` has no caller in the plugin.
- Permission: Approve/Deny, or session ends.
- Paused (restart cut it off): Resume, Dismiss, or **Resume all** (3 at a time). A resumed session keeps its place until a new done/question/permission item shows, until it is no longer running (polled every 3 s after a 30 s grace, one shared request for all lanes, `POST /v1/running-sessions`; only sessions of this app, a session of another app falls back to the item or the timeout) or, at the latest, after 2 minutes; the bar says how many wait for a place.

## Task-list filter rules (revision 2026-10-14)

### Rule 1: a done message with nothing for the user is not listed
- **Verdict, at capture time.** The summary LLM call that already writes TITLE and SUMMARY for a done item also answers `ACTIONABLE: yes|no` (summary.js; the prompt says no for a status or progress update, or a plain report of finished work that asks nothing of the user, and yes only when the reply, mainly its ending, explicitly asks a question, needs a decision or approval, reports a blocker that needs the user or tells the user to do a manual step; a plan the assistant carries out itself is not an action for the user). The verdict is stored on the item as `actionable` (true/false; absent = no verdict).
- **Conservative by construction.** Only an explicit `no` hides. Missing line, unreadable value, model failure, timeout, no LLM service, or a fallback summary all give no verdict and the item stays. On top of the model, `actionable.js` (`needsUser`) is a one-sided code guard that looks only at the tail of the reply: the last 2 paragraphs (split on blank lines) after code blocks and inline code are removed (`"0 failures"`, `"no errors"` ignored too). When the tail holds a strong signal addressed to the user, a model `no` is overridden to `yes` (and logged): a question mark, a request or choice ("please", "could you", "let me know", "your call", "which option", "you need/can/should"), an approval or confirmation ("approve", "sign-off", "confirm that"), a manual step ("by hand", "restart the", "test it", "reload"), a blocker ("blocked on", "stuck", "unable to", "cannot"), open work ("still failing", "not yet done", "unresolved", "open question"). Topic words (review, error, failure, warning, risk, recommend, next steps, ...) no longer count, and neither does anything before the tail. By the owner's explicit choice a handoff, a pull request ("pull request", "PR 123", a "PR-WAIT" heartbeat) or a ticket / work item ("ticket", "work item", "AB#123") in the tail also keeps the card visible. The guard can only keep an item, never hide one.
- **How it is hidden and found again.** The item is created and shown at once as before (the card never waits for the model); when a `no` verdict arrives while it is still open, it is resolved as `{kind:'no-action', by:'auto'}` and moves to **Resolved** (kept 7 days) with its title and summary; the Resolved line says "Hidden: nothing for you to do", its tooltip shows the summary, and **Reopen** puts it back (`reopen` accepts `no-action`). Each hiding writes a log line `review-queue: capture: hid done item "<title>" (no action needed): <summary>`; a guard override writes `summary: kept a done item the model called no-action ...`. Trade-off: because the card is not held back, a hidden item can show for the second or so the model needs, then disappears (holding every done card for the model call was rejected: it delays every real item and a failed model would have to be waited out).
- **Edge cases.** An item the user already reviewed, replied to or that was superseded before the verdict arrives keeps that resolution (the hide is a no-op). A newer done item no longer replaces older ones (revision 2026-10-16); an item that persisted data records as superseded by a hidden one is still reopened when that one is hidden (the supersede resolution records `newerId`), because the older message may be the one that needs the user. `count()`, `first()` and voice only see open items, so hidden ones are never read.

### Rule 3: a question is closed only by a real timeout, the user, the session or an answer (revision 2026-10-15)
- **Why they vanished.** Before this rule every end of the request that was not a recognised timeout (`code === 'ASK_TIMED_OUT'` read off the rejection) resolved the item `cancelled`, so the card left the open list. Proven from the real `queue.json`: 14 of 68 questions were `cancelled` (none `expired`), after 119-120 s (x8), 300 s and 360-400 s (x5), and no question item had a `key`/`callId` or an `expiresAt`, so the plugin never saw the call id of the request (late answers, `settleQuestion` and the expiry time all need it). Inferred (not provable from the data): the rejection reached `next()` or the request signal in a shape the code did not read (wrapped in `ASK_ABORTED`, a message-only error, a disconnect or a parent abort at the deadline).
- **Classification** (`classifyClose` in capture.js): `ASK_TIMED_OUT` anywhere on the error or its `cause` chain (an Error, or the bare wire record `{name:'UserQuestionError', code}`), a `TimeoutError`, or the text "timed out" (not when it carries a system code such as `ETIMEDOUT`) means the question timed out: resolved `expired` with the recommended option noted. `ASK_CANCELLED` is the user's cancel: `cancelled`. An abort-type end (request signal, `ASK_ABORTED`, `AbortError`, a dropped event source) after the known `expiresAt`, or, when no deadline is known, between 117 and 125 s after the request started (DSH's default 120 s window; the tool's configured timeout is not exposed to plugins, so no expiry is set from it and this inference uses the fixed 120 s, not `questionWindowSeconds`), is taken as the timeout too. Anything else (disconnect, parent turn abort, `ASK_ABORTED` with no evidence, a generic error) does not close the item: it stays open with `detached: true`.
- **Call id and expiry.** A request without `wait.callId` takes the call id (and a `timeout` argument) of the agent's oldest `ask_user_question` call seen at `tools/pre-execute`; a call that returned without a request is forgotten at its `tool/result`.
- **Detached questions.** The card shows "The live request ended; your answer is sent to the session." Answering it (`/v1/answer`) calls `userQuestions.answer(agent, callId, {answers})`, the late-reply path: accepted means resolved `answered by card`; DSH no longer holding it (`false`, session gone, caller not live) refuses the answer (`not-pending` / `no-session`) and resolves the item `expired`. A reply still in flight is shielded from `settleQuestion`; two answers at once send one. `settleQuestion`, the plain-message `agent/pre-step` rule and `agent/disposed` close a detached item like any other (there is no pending promise to look up). `cancelStalePending` on a restart still cancels open questions.
- **Diagnostics.** Each question that ends without an answer logs `capture: question <id> ended without an answer: name=.. code=.. message=".." after <n>s via abort|rejection -> timeout|cancelled|detached (<basis>)`; no titles, answers or secrets.

### Rule 2: a question handled in its own session leaves the list at once
- **How questions are tracked.** DSH shows the card for a pending `ask_user_question` via the `user-questions/request` waterfall; the plugin wraps it. When the user answers on the on-screen card, the wrapped `next()` settles and the item is resolved `answered by screen` (already the case). The gap was everything that settles the question without going through that promise while the item is still listed: the user replies in the session itself (the late-reply path of a timed question, or free text), or the wait ran out and the question was answered later in the session.
- **Signals used (all host side, no timeout).**
  1. `session/event` `user/message` with source `user-question-reply` and the question's `callId`: DSH's own record that the question was answered. Open item: resolved `{kind:'answered', by:'session', answers}`. Expired item (it sits in Resolved offering a late answer): re-labelled `answered by session`, keeping `assumed`, so no late answer is offered any more.
  2. `session/event` `tool/result` for the question's call id while the item is still open: the call returned. A pending payload (`{pending:true}`) means the wait ran out and the item expires like a timeout (recommended option noted); anything else resolves it `answered by session`. This also covers the legacy blocking schema, which the DSH `userQuestions` projection does not track.
  3. `agent/pre-step` (the handler that already resolves done items): a claimed message that is a reply to this question, or a plain user message (source `user` or none, not injected context such as time or instruction messages), resolves the open question items of that session.
- **Matching.** Always by session id and, for 1 and 2, the call id, so a question of another session (even with the same call id) or another question of the same session stays. Only questions of that session are touched in 3.
- **Not disturbed.** The request promise stays DSH's to settle: a session-resolved item is dropped from the card-answerable set (`answerQuestion` then says `not-pending`) but `next()` and abort still flow through untouched. Answering from the card works exactly as before: the item is resolved first, later events find it settled. A late answer sent from the card is shielded while it is in flight (its own reply event must not re-label it `late-answered`).
- **Other item types.** Permission items: an approval already settles through the same wrapped waterfall when answered on screen, and a plain user message does not decide a permission, so no session signal is added. Done items are already resolved by the user continuing the session (`replied by session`) and by the card; unchanged.
- **Edge cases.** A question still pending in another session is untouched. If the plugin's session ids differ from the agent ids the matching simply never fires (items then end by answer, expiry or session end as before). Events from a session the plugin does not receive (not loaded yet) cannot help; after a restart open questions are cancelled anyway.

## Todo item (revision 2026-10-14 (e))
A fourth item type, **todo**, lets the user start a session from the list and rely on the list for all follow-ups (the new session's questions, permissions and done results already flow in from every session).
- **Add.** "+ New todo" in the overlay header: task text (max 4000 characters), workspace dropdown ("Choose for me" default), "Use SPARC" (default off), "Effort" (desktop only; default = the default model's current effort, listed by GET /v1/model-efforts; applies to that session only, the default stays as it was). POST /v1/todo; service addTodo(text, { workspaceId?, sparc?, effort? }) so voice can call it later.
- **Item.** { type:'todo', text, sparc, state, workspaceId?, workspaceTitle?, workspace?, suggested?:{ workspaceId, title, reason }, suggesting?, error?, sessionId?, sessionTitle? }. States: awaiting-confirm (open, needs the user), starting (open, transient, not counted as waiting), started (resolved, keeps sessionId), failed (open, error and Retry), cancelled (resolved).
- **Workspace rule.** Given: create at once. Not given: suggest, then ALWAYS wait for an explicit confirm; nothing is created without it. Suggestion: (a) a workspace whose title or folder name is in the text as a whole word, case-insensitive, unique (a name inside a longer matched name of another workspace does not count) = "named in the text"; else (b) the workspace where earlier started todos with the same URL project (origin + first path segment) started, when exactly one = "same project as an earlier todo" (different workspaces for the same project = ambiguous, no pick, no model call otherwise); else (c) the cheapest LLM (summary.js pattern, pickModel) gets the task, the workspaces and the last 8 started todos (text cut to 120 characters, with their workspace) and answers JSON { workspaceId, reason }, validated against the list, 30 s limit, 600 tokens; else (d) none: the item records suggestNote (timed out after N s | no model available | the model found no clear fit | the model answered something unusable | LLM error: ...) and the card asks the user to pick, "Pick a workspace (no suggestion: <note>)"; the note and the first 200 characters of the model's answer go to review-queue.log.
- **Create.** Like dsh-hooks-tts spawnSession: create({ workspaceId }), rename (first line, max 60 characters; a task that mentions an ADO ticket: "Fix: <ticket title> - <number>", ado-ticket.js), prompt({ requestId, sessionId, mode:'queue', content }) with a caller AbortSignal (30 s). Not focused or opened. SPARC puts the task first (so the done card titles from it), then the /sparc flow and the modes:sparc text. A failure after create keeps the sessionId; Retry reuses it.
- **Routes.** POST /v1/todo, /v1/todo-confirm ({id, workspaceId?}, also Retry), /v1/todo-cancel, GET /v1/workspaces, GET /v1/model-efforts.
- **Pasted images (desktop, New session).** The task box takes pasted images (clipboardData files of type png/jpeg/webp/gif; a paste that also holds text pastes the text): each is POSTed raw to /v1/todo-image (own route because bodies are capped at 64 KB; max 8 MB, type judged by magic bytes, 5 per todo) and saved as `<stateDir>/todo-images/<uuid>.<ext>` (todo-images.js). POST /v1/todo carries `images: [ids]`; the item stores `imageIds`; start() sends `content: [{type:'text'}, ...{type:'image', mediaType, data: base64}]`, then removes the files and clears `imageIds` (also on cancel; a failed start keeps them for Retry; a file that is gone fails the start before a session is created). Hub: `images` rides in todo-start / todo-suggest (dropped for a paired phone); the upload route is served locally and is not a hub action. Errors: bad-images, too-many-images, unknown-image, bad-image, too-large. Not for follow-up todos and not on the phone form.
- **Draft (desktop).** The form {text, workspaceId, sparc, effort?, open, original?} is written to localStorage `dsh-review-queue.todoDraft` synchronously on every change (no debounce) and again on pagehide / beforeunload / visibilitychange hidden, and restored at load (busy, error, tuning never). Only a successful submit clears it; Cancel, Esc, closing the overlay, a refused or failed submit and snapshot refreshes keep it. The phone keeps its own draft under `rq-m.todoDraft` the same way (see mobile.md).
- **Tune prompt (desktop only).** A button next to "Add todo": POST /v1/todo-tune { text } -> { ok, text, questions? } | { ok: false, error } (questions: [{ question, default? }], at most 5, the open choices of the prompt-tune rules, moved out of the prompt: the form shows them in a panel under the box with an input per question (the suggested default is the starting answer), "Add answers to the prompt" appends the non-blank answers as a Decisions list and "Skip" drops them; never saved in the draft) (400 empty / too-long over 4000, 409 no model available or the model failure; adds nothing to the list; local to the app in every hub mode, not in HUB_ACTIONS, not a phone action). todo-tune.js createTuner (summary.js pickModel and llm.prepareCall like the suggester, 60 s, 1500 tokens) gives the model the rules section of config promptTunePath (default ~/.claude/skills/prompt-tune/commands/prompt-tune.md, from "## 2. Parse the profile flag" up to "## 5. Show the before/after"; embedded copy when it cannot be read) and the text; only the rewrite comes back: lines of the rules that ask for a rationale or a "because" reason are left out, the system prompt ends with an override (no rationale, no explanation, no notes), and a code fence, an "Optimized:" label, a trailing closing block (Rationale, Notes, Changes, Why, Explanation... or a remark after a "---" line) and a ", because ..." after a Suggested default are removed (at most 4000 characters). The old text is kept as `original` (the first one stays through repeated tunes) for "Undo tune"; the box and Add todo are disabled while it runs.
- **Follow-ups.** The created session is a normal session: capture lists its done, question and permission items (nothing excludes it; only subagents are skipped), each carrying its sessionId.
- **Follow-up todo (desktop UI).** The form has a two-option switch "New session | Follow up" (aria group "Kind of todo"; default New session). Follow up: the textarea reads "What should the existing session do next?", a one-line input "Which session? Describe it in your own words" (aria-label "Which session", required, max 300 characters) replaces the workspace dropdown and Use SPARC, the hint is "Nothing is sent until you confirm the session.", the button is "Add follow-up", and only { text, followUp } is posted to /v1/todo (empty description: "Say which session this is for."). Tune prompt works on the text in both modes. The workspaces are never loaded for a follow-up. Draft: `mode: 'followup'` and `followUp` are saved with the draft (only when set, so New session drafts keep their shape; a draft without them restores as New session); a successful submit resets the form to New session. Card (kind 'followup', awaiting-confirm): title "Follow up: <first line>" (speech.js titleFor), line "Session: <title> (<workspace>) — <reason>" / "Finding the session…" / "Pick a session (no suggestion: <note>)", a dropdown of item.candidates in the given order (label "<title> · <workspace>"; value = the user's pick, else the tried session of a failed item, else the suggestion; a pick no longer among the candidates is ignored), **Send** (disabled until a session is selected; POST /v1/todo-confirm { id, sessionId }) and Cancel; starting reads "Sending…"; failed shows "Could not send: <error>" with Retry (the same session) and Cancel. A sent follow-up is resolved as "Sent to <session title>" with the Open session button (item.sessionId) and Read aloud. Voice reads "Follow up: <text>, send to <session title>?" (sent: "..., sent to <title>."). Keys as for every todo.

## Voice control (designed together; wiring ships later, but the seams ship now)

Builds on the existing two-stage voice flow in dsh-hooks-tts (docs/voice-two-stage-flow.md: echo, LLM decide, deterministic read-back, strict yes, execute) and [[Dsh Voice Control Design Spec]]. Decisions from the user: read-only queries run immediately; items are spoken by queue position; confirmed actions are answer, approve/deny, mark Reviewed, open session.

### Design rules
1. **One source of truth.** The queue's host half owns the item store and exposes a small in-process service (`reviewQueue`) plus the HTTP routes the sidebar uses. The sidebar and voice are both clients of the same service, never separate copies. Voice never reads the DOM.
2. **No second action path.** Permission items reuse the voice approvals registry (`approvals.js` peek/token and the "not-approvable" rule: an approve needs a complete summary of a known tool). Question answers go through the same call the card button uses. Reviewed and Open are service calls too.
3. **Speakable by construction.** Every item carries, besides its card fields: `spoken.headline` (about 15 words, e.g. "Question from dsh-plugins: which port? Options one, two, three."), `spoken.full` (whole question with numbered options, or the 2-3 line completion summary), all passed through sanitize.js (`speakableText`, `spokenName`). The completion summary is written once by the LLM and reused for the card, the voice alert and "read item".
4. **Numbering = position.** Item "one" is the oldest open item (same order as the screen). Numbers shift when an item leaves; the service returns a `snapshotId`, and a mutating voice action freezes the item's real id plus snapshotId. If the item changed or left before the "yes", execution refuses: "That item changed. Nothing done." (same pattern as the approval token).
5. **Read-only runs now, mutations take the two-yes flow.**

### New actions
| Kind | Voice examples | Flow |
|---|---|---|
| `queue_status` | "what's in my queue", "how many waiting" | immediate: "Three waiting: one question, one permission, one done." |
| `queue_read` | "read item two", "next", "repeat", "full text" | immediate: headline first; "full text" speaks `spoken.full` |
| `queue_answer` | "answer item one, option two", "pick the recommended one" | two-yes; read-back says the question and the exact option text |
| `queue_approve` / `queue_deny` | "approve item three" | two-yes, via approvals.js rules (summary read in full) |
| `queue_review` | "item four reviewed" | two-yes |
| `queue_open` | "open item two" | two-yes (cheap, but it switches the screen) |

The decider's SYSTEM prompt and actions.js ACTIONS set get these entries; the queue snapshot (handles q1..qN, type, session title, headline, seconds to expiry) is added to the decider context beside `sessions`. Item text is untrusted data like session titles: sanitised and capped before it enters the LLM payload.

### Alerts and expiry
- A new item triggers the existing terse alert with the queue position: "Item three, question: ...". When several arrive together they coalesce ("Two new: question, done").
- Expiry warning: a question 30 s from timing out is announced once ("Item one expires in 30 seconds, recommended option two"). On expiry the item moves to Resolved and the spoken line says which recommended option was taken. With the auto-answer on (default) a timed question with a recommended option and a known window is answered 10 s before the deadline, so this 30 s warning is the last one the user gets for it.
- Speaking while a flow is active is held, as D7 of the two-stage spec says.

### Seams built in v1 (no voice code yet)
- `reviewQueue` service API: `snapshot()`, `onChange(cb)`, `answer(itemId, optionId, snapshotId)`, `approve/deny`, `markReviewed`, `openSession`, each returning a short error for stale items.
- `spoken` fields generated and cached at item creation, with tests for sanitising and length caps.
- The sidebar uses only this service, which proves the API is enough for voice.
- Selected/targeted item is service state (`focusItemId`), so "read next" and the highlighted card stay in sync, and a voice "read item two" scrolls and expands that card.

## Idle-session resume (idle-resume.js)

Every `idleCheckMs` (10 min) the host half lists the sessions of its controller and looks at the top-level ones that are not running, have no running child session, are not blank or archived and were last updated at least `idleMinutes` (30) and at most 3 days ago. A session whose log shows a background job (`started background job <id>` after the app started, not killed, not collected with a finished status, not cleared by an empty `job_list`) is skipped and looked at again next time. A session cut off in a turn (open turn, interrupted, pending next-turn message) is resumed with the standard resume prompt. Any other is judged by the cheap model from its title, folder, how the last turn ended, the last request and the last reply: `resume` (stopped in the middle, nobody's answer needed) -> the session is prompted (queued) with the idle prompt (check git status and the last tool calls, finish, or say it is finished or waiting for an answer; start nothing new) and a paused card of the session closes; `done` (finished, or waiting for the user) -> nothing; `unsure` -> a paused card with `payload.kinds = ['idle']` and the reason (the paused scan never closes it; Resume / Dismiss work as for any paused card). A session is resumed at most 3 times in 24 hours; the 4th time it is an `unsure` card. Each idle state (session id + updatedAt) is decided once; the decisions are saved in `idle-resume.json`. Off with `idleResume: false` / `DSH_RQ_IDLE_RESUME=0`, and in `node --test` runs unless `idleResume: true`.
