# Task list on Android: spec and plan (2026-10-14 grilling)

Status: built (the phone app, push, and with the hub of [hub.md](hub.md) slice H4 the pairing, devices and notifier); the decisions below come from the user, the rows Reach, Sign-in, Lost phone and Presence were changed by the hub design (see the notes in the table). Items marked **VERIFY** or listed under "Still open" are not settled. Builds on [spec.md](spec.md) and the server API in [server.js](../server.js).

## Recommendation
A **mobile-first PWA** served by this plugin, reached over Tailscale HTTPS and installed to the Android home screen. Not a Kotlin app: the server API (long-poll snapshot + small POSTs) already is the phone's API, the card logic and tests are reused, and one UI stays in step with the desktop task list. Revisit a thin native shell (Capacitor / Kotlin) only if one of these happens: web push is not delivered reliably after Android battery optimisation, a persistent notification or home-screen widget becomes a requirement, or full phone voice control is wanted.

## Decisions (from the user)
| Topic | Decision |
|---|---|
| Reach | Tailscale (private VPN) with HTTPS, no public exposure (no Funnel). **Changed by the hub:** the phone does not go through DSH at all. `tailscale serve --bg --https=443 http://127.0.0.1:47615` publishes the **hub** (loopback only) on `https://<pc>.<tailnet>.ts.net`, the app is served by the hub at `/review-queue/m/`, and the hub admits only Host names it knows (`127.0.0.1:<port>`, `localhost:<port>` and the host of `publicUrl` in `hub.config.json`; DNS rebinding) and, when `allowedTailnetLogins` is set, only those Tailscale logins. No `--trusted-host` of DSH is needed. |
| Sign-in | **Changed by the hub (D3):** pair once with a one-time code, no DSH cookie. The desktop task list (**Phone**, **Pair a phone**) shows a code (8 characters, valid 5 minutes, single use); the phone enters it at `#/pair`, names itself and gets a long-lived device token (`Authorization: Bearer rqd_...`, kept in the browser's localStorage, stored on the PC only as a SHA-256). 401 `auth-required` (revoked, or unused for 180 days) brings the phone back to the pairing screen. When the page is served by a DSH app itself (hub off) the old cookie sign-in still applies. |
| App | Installable PWA at `/review-queue/m/` inside this plugin (one plugin, shared logic and tests). |
| Scope | Every card action of the desktop task list: answer (incl. multi-question, late answer), approve, deny, approve all identical, reply, reviewed, reopen, archive session (PR merged), Keep session, filters and search, Resolved list. The chat view of a session ("Chat thread" below); read aloud with Android's own speech; free-text boxes (the reply, "Other answer…", a new todo) dictated with the in-page mic button or the keyboard's microphone; start a new todo from the phone ("New todo on the phone" below). No phone voice commands, no PC overlay show/hide. |
| Phone UI | Bottom tabs *Waiting* / *Resolved*; tap an item for a full-screen card with large action buttons; a notification opens that card. |
| Approving | Every approve on the phone shows a confirm sheet with the full command and risk labels. A risky item (the existing risk list) needs a press-and-hold on top of that. The phone sends `via: 'phone', confirmed: true`; the server rejects a phone approve of a risky item without it (defence in depth: same auth, not a second security boundary). |
| Push | Web Push from the PWA (service worker, VAPID). Types: permission, question, PR merged, done. |
| Notification text | The user wants the notification to take them to the item, with the details and the decide/prompt UI in the app. The lock screen shows the type and the number waiting only (e.g. "Permission waiting - 3 items"), never a command, reply or title, because the text passes through Google's push service. The tap goes to `/review-queue/m/#/item/<id>`. |
| Notification buttons | None. Tap opens the card, never acts. |
| Done items | Only items that need the user. The summary step already returns an `actionable` verdict and the desktop list hides "no action" items (`hideNoAction`); the phone uses the same snapshot, so it never lists them. The push for a done item is sent only after that verdict: not at capture time. Verdict false: no push. Unsure answer, model failure or timeout: the item is shown, so it is pushed. |
| UI toolkit | Preact, vendored as one file in the plugin, no build step. Card logic is plain JS shared with the overlay. |
| Push library | Written on `node:crypto` (VAPID JWT, RFC 8291 encryption, tested against the RFC test vectors); the plugin stays dependency-free. |
| Devices | One user, several phones. Each device (push subscription) has its own on/off switch per type in the phone's settings page; the desktop device list can remove any device. |
| Quiet hours | Configurable window (per device). Permission and question may break through it (a session is blocked); done and PR merged wait and arrive as one digest when it ends. |
| Lost phone | **Revoke** on the desktop (**Phone** in the task list) signs that phone out at the hub: its token stops working on the next request, its open long poll ends, its push subscription is deleted. Nothing in DSH's own login is involved, so no other login is touched (the old open question is settled by the token design). |
| Open session | No button on the phone; sessions are opened at the PC (`open-session` is desktop-only at the hub). A phone may start, confirm and cancel todos, never open the session they create. |
| Retention | Same 7 days of Resolved as the desktop; one shared store. |
| Presence | While the desktop task list is being looked at, the push is held; if the item is still open after 60 s without a look it is sent. Built: the overlay's long poll says `&visible=1` while its page is visible, the hub notes the time of the last such poll of the desktop role (a phone's flag does not count), and `hub/notifier.js` holds a push until 60 s have passed. |

## Design
### Server (this plugin)
- Static routes under the existing prefix (all behind `connection.admit`): `/m/` (page), `/m/manifest.webmanifest`, `/m/sw.js` (scope `/review-queue/m/`), icons. Same API as the desktop (`/v1/snapshot`, `/v1/answer`, ..., `/v1/archive`).
- `push.js`: VAPID key pair created once and kept in the state dir; subscriptions in `push.json` (endpoint, keys, created, user agent, last success); a 404/410 from the push service deletes the subscription. Routes: `GET /v1/push/key`, `POST /v1/push/subscribe`, `POST /v1/push/unsubscribe`, `POST /v1/push/test`, `GET /v1/push/devices` (so a lost phone can be removed from the desktop page).
- Notifier: subscribes to the store, decides what to send. One notification per type, replaced by tag instead of piling up ("Permission waiting - 3 items"); TTL 12 h; urgency high for permission and question, normal for done and PR merged. A resolved item cannot clear a shown notification (a push must show something on Android), so a stale tap lands on an "already handled" screen with the resolution line.
- Presence: the desktop client adds `client=desktop&visible=1` to its long-poll; the server keeps the time of the last visible desktop poll. Held pushes are re-checked at +60 s and dropped when the item is gone.

### Client
- The pure card logic now inside lib/client.js (resolution text, filters, answer validation, error text, drafts) moves to a shared module used by both the DSH overlay and the phone page; the overlay keeps its tests. The phone views are new (list, card, confirm sheet, install and notification set-up, connection banner).
- Connection loss: a banner, backoff reconnect, unsent replies and half-picked answers stay in local storage (as on desktop). An action that fails because the item changed shows the same text as the desktop.
- Read aloud: `speechSynthesis` with the `spoken.full` text the snapshot already carries. On Android (Chrome and the TWA) that is the device's own TextToSpeech engine. On iPhone and iPad the button is not drawn.
- No Open session button on the phone.
- New todo and dictation: see the two sections below.

## New todo on the phone
The same flow as the desktop task list's "+ New todo" (see [spec.md](spec.md) and the vault note *Task List Todo Design*), over the same API; the hub lets a paired phone call `POST /review-queue/v1/todo`, `/v1/todo-confirm` and `/v1/todo-cancel` (`DEVICE_ACTIONS` in [hub/http.js](../hub/http.js)); `open-session` and every other action stay desktop-only (403).
- **Form** (Waiting screen, **+ New todo**, route `#/new`): a textarea for the task (several lines, 4000 characters like the server), a workspace dropdown (*Choose for me* first, then every workspace by title from `GET /v1/workspaces`; a failed load or an empty list says so and offers a reload), *Use SPARC* (off), a mic button and **Start todo** (disabled while the text is empty or a request is running). It posts `{text, workspaceId?, sparc?}`; on success the phone goes back to the list. Errors use the desktop's words (`core.errorText`), with friendly sentences for `empty`, `too-long`, `unknown-workspace`, `no-registry` and `owner-offline`. The draft is kept while the user moves between screens and is saved to localStorage (`rq-m.todoDraft`) on every change, flushed on pagehide and when the page is hidden, and restored when the page starts (reload, crash); only a successful start clears it, a refused or failed one keeps it. There is no Tune prompt button on the phone (and `/v1/todo-tune` is not a phone action).
- **Effort**: below *Use SPARC* (New session only) an *Effort* dropdown lists the reasoning efforts of the default model (`GET /v1/model-efforts`, answered by the hub from the coordinator app, asked again each time the form is shown): *Default (<name>)* first, then each effort. The pick is sent as `effort` only when it is not Default, is kept in the saved draft only when set, goes back to Default after a start, and applies to that session only (the default effort stays as it is, see the README). No dropdown for a model without efforts, a failed load or Follow up. A todo card says *Effort: High* when one was asked for.
- **No image paste.** The phone form has no image attach; pasting images is a desktop New-session feature (README, *Pasted images*). The hub drops an `images` field of a phone todo.
- **Card**: a todo awaiting confirmation or failed shows the suggested workspace line, a dropdown preselected like the desktop (the user's pick, else the workspace the todo was given, else the suggestion), **Start** (**Retry** when failed) and **Cancel**. Starting, started and cancelled are read-only text; there is no Open session button.
- **Code**: pure logic in [lib/mobile/todo-form.js](../lib/mobile/todo-form.js) (`newTodoPayload`, `workspaceChoices`, `workspacesNote`, `todoErrorText`) and `todoCardModel` in [lib/mobile/model.js](../lib/mobile/model.js), which reuses the overlay's `todoLine`, `todoSelect` and `todoTarget` (exported in `exports.shared` of [lib/client.js](../lib/client.js)); views.js stays thin.

### Follow-up todo on the phone
The form has a **New session | Follow up** switch (two toggle buttons above the text box). Follow up sends the text as a queued prompt to an **existing** session found from plain words (backend: [hub.md](hub.md) 6.4a); the candidates come only from the hub (the phone cannot supply sessions; the hub ignores any in the request).
- **Form**: in Follow up mode the textarea reads "What should the existing session do next?", a "Which session? Describe it in your own words" input (300 characters, its own mic button, the same dictation as the text box: it fills the field and never sends) appears, the workspace dropdown, *Use SPARC* and the workspaces request are gone, and the hint says "Nothing is sent until you confirm the session." The button reads **Add follow-up** and posts only `{text, followUp}`; a missing description is "Say which session this is for." (more than 300 characters: "Describe the session in 300 characters or fewer."). `empty-query`, `unknown-session` and `no-session` use the desktop's words. The draft keeps the mode and the description in `rq-m.todoDraft` **only when they are set** (`mode: "followup"`, `followUp`), so a draft saved before the feature restores as New session; a successful add clears both.
- **Card** (`kind: 'followup'`): the text, the suggestion line ("Session: <title> (<workspace>) — <reason>", "Finding the session…", "Pick a session (no suggestion: …)"), a **Session** dropdown preselected like the desktop (the user's pick while it is still a candidate, else the session sent to before, else the suggestion), **Send** (disabled until a session is selected; **Retry** when failed) posting `/v1/todo-confirm {id, sessionId}`, and **Cancel** (`/v1/todo-cancel {id}`). Starting reads "Sending…", started "Sent to <session title>".
- **No conversation (user decision, conservative default).** A phone can ask for a follow-up in any open session of any connected app (set `allowedTailnetLogins` in `hub.config.json`), but it **cannot read or post to that session afterwards**: a follow-up card, in any state, shows only "Sent to <session title>", with no Conversation and no composer (`hasThread` / `canPost` in [lib/mobile/thread.js](../lib/mobile/thread.js) are false for a todo), and the hub refuses `thread` and `post` of a follow-up to a phone (`no-session` / `not-a-session`, [hub.md](hub.md) 6.8). The desktop role is unchanged.
- **Prompt-injection hardening.** The model's reason is shown as "Model says: <reason>"; a model suggestion for a **running** session is not preselected (the dropdown starts on "Pick a session…", the line reads "Model suggests: <title> …", Send is off until a pick). "Too many follow-ups are waiting: confirm or cancel one first." is the error when 10 already wait.
- **Code**: `FOLLOWUP_MAX`, `isFollowUpDraft`, `withTodoMode`, `newTodoPayload` in todo-form.js; `todoCardModel` (kind, selectLabel, needsWorkspaces), `todoConfirmBody`, `todoCancelBody` in model.js. Tests: `mobile-todo-follow-up*.test.mjs`, `thread-follow-up.test.mjs`.

## Dictation (speech to text)
A mic button sits next to every free-text box: the new-todo text, "Reply to this session…" and each question's "Other answer…". **It fills the box and never sends**: the recognised text is pasted at the end of what is already there (one separating space when needed, existing text never lost), and the user reviews it and presses the normal Send button. While listening the box shows the interim text live and replaces it as it refines; the final result commits. Tapping the button again stops. One recognition runs at a time (starting one stops another); leaving the screen stops it.
- **Engine**: the Web Speech API (`window.SpeechRecognition` or `webkitSpeechRecognition`). In Chrome and the TWA on Android that is Google's speech service, the device's system speech-to-text (with the newer Google speech models where they are installed). `lang` is `navigator.language` (fallback `en-US`), `interimResults` on, `continuous` off (unreliable on Android Chrome). **A web page cannot detect or call the Gemini app**, and nothing here sends the text to an LLM: plain STT only. Without the API the mic buttons are hidden. A later APK shell may use Android's `RecognizerIntent` instead of the web API.
- **Errors** appear under the box: permission blocked (`not-allowed`, `service-not-allowed`: allow the microphone in Chrome's site settings), "Didn't hear anything" (`no-speech`), no microphone (`audio-capture`), speech service unreachable (`network`), language not supported; `aborted` is silent.
- **Code**: [lib/mobile/dictation.js](../lib/mobile/dictation.js) (`dictationSupport`, `mergeDictation`, `dictationError`, `createDictation`: `start`, `stop` (the engine may still deliver its final result) and `halt`, which aborts and drops everything the engine reports afterwards) is pure and tested with a fake recognition class; it has no network, no api.js and no endpoint, so it cannot send. `Mic` in views.js is the only user. Real-device check: T11 in [hub.md](hub.md) 11.3.
- **Dictation and Send**: a recognition that is still listening or finalizing must not touch a draft that was just sent. Send halts the Mic (a ref the composer gives it) before it flushes and posts; the Mic also halts itself when its button gets disabled (a post or an answer runs) and when it is removed; the composer ignores dictated text while a post of its item is running. So a late result neither writes the sent text back as an unsent draft nor makes `postFollowUp` keep the draft after success.

## Paused sessions (resume at the PC, dismiss on either)
Sessions a DSH restart cut off in the middle of work are listed as items of type `paused` (the detection, resume and dismiss are described in [hub.md](hub.md) 6.7). The phone **shows** them and can **Dismiss** one (they need no action; `paused-dismiss` is in `DEVICE_ACTIONS`), but it cannot resume one (`paused-resume` is not, so it answers 403 `desktop-only`; no code of the phone page calls it). No push is sent for them.
- **Indicator**: the header reads "N waiting · ⏸ M paused" (paused sessions do not raise the waiting count); the Waiting list starts with a banner "M sessions were paused by a restart. Resume them at the PC, or dismiss them here." and a **Show** button that sets the *Paused* filter chip.
- **Card**: chip *Paused*; the facts the desktop card shows (why it is listed, how long ago it last wrote, a tool call that may be half done, the last request) "To resume this session, use the Coding Boss Review Queue on the PC. If it needs no action, dismiss it here." and a **Dismiss** button (back to the list on success).
- **Code**: `pausedNote`, `pausedView` and the `paused` count of `listModel` in [lib/mobile/model.js](../lib/mobile/model.js) (the facts and the count come from `pausedFacts` / `pausedCount` of the overlay's `exports.shared`); `PausedBody` in views.js.

## On hold (its own tab)

Sessions parked with Hold (desktop, phone, `/onhold` or an `ONHOLD` line; see the README section *On hold* and [hub.md](hub.md) 6.7b) are items of type `onhold`. They are **not** waiting, not in *All* and have no filter chip: the nav bar gets an **On hold** tab (with its count; shown while any session is held, or while the tab is open), route `#/onhold`, a list with a search box.
- **Card**: chip *On hold*; the facts of the desktop card (reason, ticket and check interval, how long held, last check, errors) from `heldFacts`; **Continue** (`/v1/hold-continue`) and **Release** (`/v1/hold-release`). No composer: a held session cannot be written to from the phone (`canPost`, error `onhold`); the conversation can be read.
- **Hold button**: on a *Done* card and on a *Paused* card (`/v1/hold {id, reason}`; the reason is optional).
- **Code**: `heldView` and the `held` / `heldOpen` fields of `listModel` in [lib/mobile/model.js](../lib/mobile/model.js); `HeldBody`, `HeldList`, `OnHoldButton`, `OnHoldForm` in [lib/mobile/views.js](../lib/mobile/views.js).

## Session count in the top bar
The top bar shows `N working / M open` (sessions of DSH with a turn running / open sessions, summed over every connected app) under the waiting count, in its own line with tabular digits and a reserved height, so nothing moves when it changes (it fits at 390 px). The words come from the desktop's shared helper (`sessionsText`), the numbers from the snapshot's `sessions` (hub sum; hidden while unknown). The phone never shows the tip of the day; its long-poll token carries the numbers so a change reaches it by itself.

## Chat thread
A phone-only chatbot view of a session's past conversation, with follow-up posts. The conversation is on the card of every item that has a session, open or resolved, except a todo that has not been sent (question, permission, done, paused, PR merged, resolved, and a follow-up todo that was sent to its session); the composer is on all of those except a **paused** item (see Posting). It shows the **last 40 text messages** of that session: the user's messages as right-hand bubbles (plain text), the assistant's text as left-hand bubbles (rendered as markdown), oldest at the top, the newest at the bottom, each with its age. Tool calls, tool results, thinking and automatic notices (hooks, system, working directory) are not shown; a message over 4000 characters is cut and says so ("… the rest of this message is not shown."). The desktop task list is unchanged.

### Screen
- **Placement.** The card keeps its summary and action buttons first; below them is a collapsible **Conversation (n)** section (the count has a "+" when earlier messages exist) and, at the bottom of the card, the composer (not for a paused item: it is read only there, resume it at the PC). The section is **open** for done and resolved items (the chat is the point there) and **closed** for questions, permissions, paused and merged-PR items, so on a small screen the transcript never pushes Approve / Deny / Send answer out of reach; tap the summary to read it. The conversation loads and refreshes only while the Conversation section is open: it is mounted when the section opens (first load, then the 5 s refresh) and unmounted, with its polling, when it is collapsed. A todo card has neither.
- **Transcript.** A scroll box of at most 60 % of the screen height (`dvh`); it opens at the bottom. New messages scroll into view when the reader was near the bottom (or just posted); otherwise the position is left alone and a **↓ N new messages** pill appears. **Load earlier** at the top (while `hasMore`) fetches the 40 messages before the oldest one shown and keeps the reader's place. States: *Loading the conversation…*, *No messages yet.*, an error in words with **Retry**; when messages are already on screen a failed refresh only adds a small note ("No connection: showing the last messages that were loaded.", or the reason) and keeps them.
- **Composer.** Sticky at the bottom of the card, above the tab bar (`env(safe-area-inset-bottom)`; the viewport meta has `interactive-widget=resizes-content` so Chrome's keyboard resizes the page instead of covering it): a textarea that grows to about five lines, the **Mic** and **Send**. **Enter inserts a newline**; only the Send button posts. The draft is `state.replies[id]` (kept in the browser like the old reply box), but **typing stays out of the global store**: the composer keeps a local draft (`createDraftBuffer` in [lib/mobile/thread.js](../lib/mobile/thread.js)), writes `state.replies[id]` 250 ms after the last keystroke (dictation updates the same local draft) and flushes it at once on blur, `pagehide` / page hidden (followed by `saveNow()`, the browser storage write), before Send and when the composer is unmounted; an accepted post clears the draft in the store and the composer follows it; a failed post keeps it. Mic = the Web Speech API `Mic` of [Dictation](#dictation-speech-to-text): it fills the box and never sends, and is hidden where the browser has no speech recognition. The buttons are disabled and the box is **read-only** (not disabled, so the phone keyboard stays open) while a post is running; a second tap is ignored.
- **The old reply box is gone.** A done card no longer has its own "Reply to this session…" box and **Send reply**; the composer replaces it (**Reviewed** and **Full reply** stay).
- **Open or closed is remembered.** The **Conversation** section, a done card's **Full reply** and an expired question's **Answer now (late)** keep the choice you made, per item and per section, across screens, reloads and app restarts (`localStorage` key `rq-m.toggles`, `{ details: { "<itemId>|<kind>": boolean } }` with kinds `conversation`, `reply`, `late`). Without a choice they keep the old defaults (Conversation open for done and resolved items, Full reply open under 1500 characters, Answer now closed). Choices of items that left the queue are dropped with each snapshot. The pure helpers are in `lib/mobile/toggles.js`.

### The keyboard
While a text field **outside the composer** has the focus (the filter search box, the new todo box, an Other answer box), the body gets the class `typing` and the bottom tab bar is hidden (`body.typing nav` in style.css, `watchTyping` / `hidesTabBar` in [lib/mobile/view-guard.js](../lib/mobile/view-guard.js), started by app.js on `focusin` / `focusout`), so that Android Chrome's `resizes-content` viewport keeps room for the page above the keyboard. The composer never hides the bar and is never hidden (it sticks to the bottom edge while the class is set). **iOS caveat: unverified on a device**: Safari keeps the layout viewport under the keyboard instead of resizing it, so the class may change little there.

### Refresh rule
The client (not the server) polls: `POST /v1/thread` for the newest page **every 5 s (slower while nothing changes, below), only while the item screen is open and the page is visible** (`shouldPoll` in [lib/mobile/thread.js](../lib/mobile/thread.js): route `#/item/<id>`, document visible, the item has a session and is not a todo, the phone is paired). One request at a time, the next timed 5 s after the last one ended. It stops when the screen is left, on `pagehide`, when the page becomes hidden and when the phone must pair again; when the page becomes visible again it refreshes at once and carries on. A refresh is silent (no spinner) and keeps what is shown when it fails. It sends `after` = the id of the newest logged message shown, and the PC answers `{ ok: true, unchanged: true }` (no page) when there is nothing newer; an unchanged answer, like a page that repeats what is shown, changes no state (the message objects already shown are kept, `setThread` skips `set()` when the thread is the same to the view), so nothing renders. **Back-off:** `pollDelay(unchangedCount)`: 5 s, 10 s after 3 refreshes in a row that brought nothing new, 20 s after 6; a change, a post of the user or starting the screen again brings it back to 5 s (a failed poll neither counts nor resets).

**Timeouts and aborts.** A thread request is cut off after 20 s (`THREAD_TIMEOUT_MS`), a post after 40 s (`POST_TIMEOUT_MS`; busy is released, the draft stays, the error says the message may have been sent); implemented with an `AbortController` and `setTimeout` (no `AbortSignal.timeout` / `AbortSignal.any`, which older iOS Safari lacks). In-flight thread requests are aborted when the page is hidden, on `pagehide` and when the phone comes back `online` (like the snapshot long poll); an abort of our own sets no error note (a first load ends with the retry note) and the `reading` guard is always released, so polling and Retry work again. **Memory:** leaving the item screen trims that thread to its newest 40 messages (`trimThread`; `hasMore` / `cursor` set so Load earlier brings the rest back), and at most 10 threads (`MAX_THREADS`) are kept, the least recently opened one is forgotten (`touchThreads`). Messages are drawn through a memoised bubble (`shouldComponentUpdate` on the message object and the minute) and `.bubble` has `content-visibility: auto`. A log is written in batches, so a message can take a moment longer to show.

### Posting
**Send** calls `POST /v1/post {id, text, key}` (trimmed, 4000 characters like a reply; `key` is the idempotency key of the composed message: `newPostKey()` = `crypto.randomUUID()`, else a random string, made once per message by `postKeyFor` ([lib/mobile/thread.js](../lib/mobile/thread.js)) and kept per item in `failedPosts` of [lib/mobile/api.js](../lib/mobile/api.js); a retry of the **same text** after an error or the 40 s cut-off reuses it, so a message that did arrive is not sent twice, the PC answers `{ ok: true, duplicate: true }` ([hub.md](hub.md) 6.8); an accepted post or a changed text gets a new key). A pending bubble appears at once ("Sending…"); when the server accepts, the draft is cleared, the bubble is marked "Sent" and the thread is refreshed immediately, and the bubble gives way to the logged message when the refresh shows it (a prompt is queued, so the log shows it only when the queue drains; the bubble is kept for up to 15 minutes, `SENT_BUBBLE_MS`, and given up after that if the log never shows it). When it fails the bubble goes, **the draft stays** and the reason is shown above the box (the desktop's words, plus *not a session* / *session not running here*). The screen is **never left** after a post: the server resolves an open done item as replied, exactly as a reply, and any other item (a question, a permission, a resolved item) keeps its state, so chatting never answers a question or approves anything by accident. A **paused** session shows its conversation but has **no composer**: `canPost` ([lib/mobile/thread.js](../lib/mobile/thread.js)) is false for type `paused`, and the PC refuses a post to one with `paused` ("Resume it at the PC first."), because resuming is the desktop's `paused-resume`, with its own guard and bookkeeping. While a post for the same session is on its way (any item of it, open or resolved) a second one answers `busy`. The conversation of an item is keyed by the item id, so moving from one item to another in place resets its open state and polling.

### API and server
`POST /v1/thread {id, before?, limit?, after?}` and `POST /v1/post {id, text, key?}`, both on `DEVICE_ACTIONS` ([hub/http.js](../hub/http.js)); the contract and the error codes are in [hub.md](hub.md) 6.8. The error codes the screen words: not-found, no-session, no-log, too-large, no-zstd, unreadable, no-reader, owner-offline, owner-away, owner-timeout, unknown-outcome, session-unavailable (`threadErrorText`); a failed post adds `post-failed` (any other failure of the PC's controller, never its text), `paused` and `busy` (`postErrorText`).
- **Cost on the PC.** Reading a log blocks the host's event loop while it is decompressed, and the phone asks every 5 s. [thread.js](../thread.js) therefore keeps a small LRU cache (8 logs, **one entry per file path**, replaced when the file changes; `createThreadCache()`, `cache.hits` / `cache.misses` for tests) of the extracted chat messages: only the newest 501 (`MAX_KEPT_MESSAGES`) plus the total count, which is all any allowed page can reach, so the answers equal those of the whole list. An unchanged log is not read or parsed again, whatever page is asked for. A log that **grew** is decoded **incrementally**: the entry remembers `{ size, mtimeMs, endOffset (end of the last complete zstd frame), recordCount, totalOutput }`; when the file is larger and its old end starts a frame (zstd magic), only the bytes from `endOffset` are read (the injectable `fs.readFrom(file, position, length)`, default a ranged `fs.read`) and decoded, the record indexes (= message ids) continuing, with the 32 MiB / 64 MiB caps counting the running total; a torn last frame does not advance `endOffset` and is read again once complete. A shrunk or replaced file, a failed or short ranged read, or the same size with another mtime is parsed in full (the result is always that of a full parse; `parseLogFrames` in [paused.js](../paused.js) reports where the complete frames end). A live session's log changes every few seconds, so that key misses on most polls; **any request for the same log** (same root and session, whatever `before` and `limit`) is therefore answered from the messages of its last read for **max(3 s, 5 x the duration of that read), at most 30 s** (`THREAD_THROTTLE_MS` is the floor, with `THREAD_COST_FACTOR` and `MAX_THREAD_THROTTLE_MS`; the duration of the last parse is kept per log, also while later reads come from the parsed cache; injectable clock `createThreadCache({ now })`, at most 8 logs; a changed log is read again once the 3 s have passed), so varying the paging arguments cannot force a re-read; requests that arrive while a log is being read share that one read (`cache.flight`). The thread reads logs up to **8 MiB** compressed (`DEFAULT_THREAD_LOG_BYTES`, option `maxLogBytes`; the paused-session scan keeps its own 64 MiB), and every zstd frame is decoded with `maxOutputLength` 32 MiB (`MAX_FRAME_OUTPUT`) and all frames of one log together may decode to 64 MiB (`MAX_TOTAL_OUTPUT`), so a high-ratio file cannot blow the memory; a bigger log or frame answers `too-large`. The `thread` command runs outside the executor's serial chain and result cache ([hub.md](hub.md) 6.8).
- **Paging depth.** A device can page back only `MAX_THREAD_DEPTH` = 400 messages behind the newest ([thread.js](../thread.js)): a `before` cursor with more than 400 messages at or after it gets `{ ok: true, messages: [], hasMore: false }` (no error; the phone shows no more history), so a stolen or misused phone cannot dump a whole transcript. The `thread` commands of the agent run beside its other commands, at most 2 at once, at most 8 waiting (the next one answers `busy`), a late waiting one is dropped and a read stuck for 20 s frees its slot ([hub.md](hub.md) 6.8).
- **Privacy.** Only the text of user and assistant messages leaves the PC, over the same paired, tailnet-only channel as the rest of the phone API, and only when the phone asks. That is the same trust as the full reply text the phone already shows on a done card; tool output, file contents read by tools and the model's thinking never leave. Message text is never logged (not by the server, the hub or the phone page); a log that cannot be read is logged as `thread: <error code or name>` only, never the error's message. Records that are surface replacements (`surfaceOp` `{op:'replace'}`, e.g. a compaction checkpoint) are not shown as bubbles.
- **Code.** Server: [thread.js](../thread.js) (read, cache, page), `thread` and `post` in [service.js](../service.js). Phone: pure logic in [lib/mobile/thread.js](../lib/mobile/thread.js) (merge by id, pending bubbles, error words, poll and scroll rules), state and requests in [lib/mobile/api.js](../lib/mobile/api.js) (`state.threads`, `loadThread`, `loadEarlier`, `refreshThread`, `postFollowUp`, `startThreadPolling` / `stopThreadPolling`), screens in [lib/mobile/views.js](../lib/mobile/views.js) (`Conversation`, `ThreadView`, `Bubble`, `Composer`). Tests: mobile-thread, mobile-api-thread, mobile-thread-wiring, thread-cache, and for the performance follow-up thread-incremental, thread-window, thread-after, mobile-thread-perf, mobile-api-perf, mobile-perf-wiring.

## iPhone
Step-by-step deployment guide: [iphone.md](iphone.md).

On an iPhone the app is the web page itself, installed to the Home Screen: no store, no Mac, no developer account.
1. **Tailscale**: install the Tailscale iOS app, sign in to the same tailnet and turn it on. The phone must reach the HTTPS name from `publicUrl` (`https://<pc>.<tailnet>.ts.net/review-queue/m/`).
2. **Open it in Safari** (not Chrome for iOS: only Safari offers Add to Home Screen with the standalone app), then **Share, Add to Home Screen**, name it. Until it is installed the page shows a one-time banner with these steps (dismiss it with *Dismiss*; remembered in `localStorage` key `rq-m.install-hint-dismissed`).
3. **Open the app from the Home Screen icon** (standalone, no Safari bars; the icon is `lib/mobile/icon-180.png`, the status bar is black). Pair it as in the runbook below: iOS may keep a Home Screen app's storage apart from the Safari tab's (unverified), so pair again from the Home Screen app if it asks.
4. **Notifications** (Settings tab, *Turn on notifications*, from a tap) work **only from the Home Screen app on iOS / iPadOS 16.4 or later**, never in a Safari tab; Settings says so on an iPhone that is not installed or too old. Push goes through Apple's service (`web.push.apple.com`), which needs a valid VAPID subject: the hub uses its https `publicUrl` origin unless `pushSubject` is set (see the runbook).
- **View guard**: an iPhone/iPod user agent counts as a phone. If the page is laid out wider than 900 px the banner says to tap the *aA* button in Safari and choose *Request Mobile Website*. An iPad (also iPadOS in desktop mode, a Macintosh user agent with touch) is a tablet and gets no warning. Safari's *Request Desktop Website* on an iPhone sends a Macintosh user agent, so the guard cannot detect it (unverified); the width rule still applies only when the user agent says iPhone.
- **Dictation**: Safari has `webkitSpeechRecognition`, but it needs *Settings, Siri & Dictation* turned on, the microphone allowed for Safari, and it may be unreliable or unavailable in a Home Screen app (unverified; check with T12). The error under the box then says so. Without the API the mic buttons are hidden.
- **Not applicable**: `assetlinks.json`, the TWA and the APK are Android only.
- **No native shell is built.** A wrapper app needs macOS, Xcode and an Apple developer account. If wanted later: a thin WKWebView (or Capacitor) app that loads the same HTTPS URL; push would still go through Apple's service exactly as the PWA does. Real-device check: T12 in [hub.md](hub.md) 11.3.

## Phone setup (runbook)

Done once, on the PC that runs DSH and the hub.

1. **Publish the hub on the tailnet** (PowerShell; the hub listens on 127.0.0.1:47615 only; the first time it may need an elevated shell):
   ```
   tailscale serve --bg --https=443 http://127.0.0.1:47615
   tailscale serve status        # check: shows https://awang-lpt2.taile1279d.ts.net -> 127.0.0.1:47615
   tailscale serve --https=443 off   # remove
   ```
   (If DSH itself is ever published on 443, give the hub `--https=8443` and use that origin in `publicUrl`.) Never use `tailscale funnel`.
2. **Tell the hub its public address.** Create `~/.dsh/review-queue/hub.config.json` (no secrets in it):
   ```json
   {
     "publicUrl": "https://awang-lpt2.taile1279d.ts.net",
     "allowedTailnetLogins": ["<your tailscale login, e.g. you@example.com>"],
     "pushSubject": "mailto:<your address>"
   }
   ```
   `pushSubject` is optional: when left out the hub signs its push messages with the https `publicUrl` origin (Apple's push service rejects a `mailto:` on localhost); an explicit value always wins. `publicUrl` is required (without it the hub refuses the tailnet host name). `allowedTailnetLogins` is recommended (find your login with `tailscale status`); leave the list out only if every device in your tailnet may pair. Restart the hub so it reads the file (it is read at start): `POST /hub/v1/shutdown` with the agent secret, or end the `node hub/main.js` process; the next DSH app starts it again. Restart DSH (and refresh the browser) once to load the new overlay and instance routes.
3. **Open the app on the phone**, in Chrome, with Tailscale on: `https://awang-lpt2.taile1279d.ts.net/review-queue/m/`. It shows *Pair this phone*.
4. **On the desktop** open the task list (Ctrl+Alt+L), press **Phone**, then **Pair a phone**. A code like `K7QM-2XD9` and a link appear (valid 5 minutes, one use).
5. **On the phone** type the code (or open the link from the desktop), keep or change the name, press **Pair**. The list appears.
6. **Notifications:** Settings tab, **Turn on notifications**, allow them, **Send test**. Optionally install the app (Chrome menu, Install app).
7. **Lost phone:** on the desktop, **Phone**, then **Revoke** next to it (press twice to confirm). It is signed out on its next request and gets no more notifications. A phone you only want to sign out yourself: Settings, **Forget pairing** (it stays in the desktop list until revoked).

If pairing says the address does not answer like the hub, you opened the DSH page instead of the hub address. If the phone says 403 *login-not-allowed*, add its Tailscale login to `allowedTailnetLogins` and restart the hub.
